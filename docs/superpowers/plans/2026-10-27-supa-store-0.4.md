# supa-store 0.4 (createJsonRpc) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 서버 앱이 JSON-RPC 2.0 상대(띄운 프로세스, 다른 서버)와 이야기하는 연결을 `supa-store/rpc` 의 `createJsonRpc` 로 꺼낸다.

**Architecture:** 세 겹으로 짓는다. 틀(`framing.ts`)은 바이트 흐름을 메시지 글자로 자른다. 통로(`transport.ts`)는 `stdio` · `websocket` 이 같은 `Transport` 꼴을 돌려준다. 세션(`session.ts`)은 통로 하나 위에서 JSON-RPC 요청 · 답 · 알림 · 상대의 요청을 맡는다. 맨 위 `createJsonRpc`(`client.ts`)는 생명주기 · 준비 문 · 다시 잇기 · 값을 맡고, 끊길 때마다 세션을 새로 짓는다.

**Tech Stack:** TypeScript 5.8 (NodeNext), Node 20+, `ws` 8(선택 peer), vitest 3(`// @vitest-environment node`).

**Spec:** `docs/superpowers/specs/2026-10-26-supa-store-0.4-jsonrpc-design.md` (아래 「스펙 §n」). 0.3 설계는 같은 폴더 `2026-10-25-supa-store-0.3-stream-design.md`.

## Global Constraints

- 하위 경로 `supa-store/rpc` 하나. 내보내는 것: `createJsonRpc`, `stdio`, `websocket`, `Transport`(타입), `RpcError`(타입과 값). React 를 들이지 않는다. `exports` 에 `browser` 조건을 두지 않는다.
- `src/rpc/**` 는 `tsconfig.server.json` 으로 짓는다(Node 타입). `tsconfig.json` 의 `exclude` 에 `src/rpc` 를 더한다.
- 문구는 0.3 의 `TEXT`(`src/stream/protocol.ts`)를 그대로 가져다 쓴다: `"연결 끊김. 재시도 중.."`, `"연결 끊김. 명령 실패"`, `"연결 끊김. 알 수 없음"`, `"응답 지연"`.
- 기본 값은 0.3 의 `DEFAULTS` 를 그대로 쓴다: 제한 시간 `timeoutMs` 30_000, 다시 잇기 `backoffStartMs` 1_000 에서 두 배씩 `backoffMaxMs` 30_000, `jitter` 0.2, 웹소켓 ping `pingMs` 25_000, 끊김 판정 `idleMs` 60_000. 시험이 간격을 줄이는 길은 0.3 의 `TIMING` 심볼 꼴을 따른다.
- 웹소켓 `maxPayload` 기본 `1024 * 1024`. 표준 입출력에는 한도가 없다.
- `stdio` 의 `killAfter` 기본 2_000 ms.
- JSON-RPC 오류 코드: 맞는 handler 가 없으면 `-32601` (`"Method not found"`), handler 가 던지면 `-32603` 와 던진 문구.
- 요청 함수와 handler 의 params 는 하나다(펼치지 않는다). 정해진 이름 `request` · `notify` · `view` · `subscribe` · `close` 는 `requests` · `notifications` 이름으로 쓸 수 없다(타입 오류).
- `[USE]` 와 `retry()` 는 두지 않는다. `[DISPOSE]` 는 `src/index.ts` 의 `DISPOSE` 를 쓴다.
- 주석은 주변 코드처럼 짧은 한국어. 커밋 메시지는 한국어, 끝 줄 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. `onConnect` 안의 `initialize` 를 보낸 뒤 프로세스가 죽는다: 그 요청은 「연결 끊김. 알 수 없음」으로 끝나고, `onConnect` 가 던진 것으로 보아 다시 잇는다. 멈춰 서지 않는다. (Task 4)
2. 다시 잇기를 기다리는 동안이나 `onConnect` 가 도는 동안 `close()` 를 부른다: 그 뒤로 `connect` 가 다시 불리지 않고, 열린 통로는 닫힌다. (Task 4)
3. `Content-Length` 머리에 `Content-Type` 같은 다른 머리가 붙거나 이름의 대소문자가 다르다: 그대로 읽는다. (Task 1)
4. 모르는 id 의 답, 제한 시간이 지난 뒤 온 답: 버리고 던지지 않는다. (Task 3)
5. handler 가 `undefined` 를 돌려준다: `result: null` 로 답한다(JSON-RPC 는 `result` 칸을 요구한다). (Task 3)

### Task 1: 틀 — 바이트 흐름을 메시지로 자른다

**Files:**
- Create: `src/rpc/framing.ts`
- Test: `src/rpc/framing.test.ts`

**Interfaces:**
- Produces:
  - `type Framing = "content-length" | "ndjson"`
  - `createReader(framing: Framing, onMessage: (text: string) => void): (chunk: Buffer) => void` — 조각을 받아 메시지가 다 차면 글자로 알린다
  - `encode(framing: Framing, text: string): Buffer`

- [ ] **Step 1: 시험을 쓴다** (`// @vitest-environment node`)
  - `content-length`: `encode` 한 두 메시지를 한 조각으로 붙여 넣으면 두 번 알린다. 한 메시지를 1바이트씩 넣어도 한 번 알린다.
  - 길이는 바이트 수다: `"{\"a\":\"한글\"}"` 를 `encode` 한 머리가 `Content-Length: 16` 이고, 읽으면 같은 글자가 나온다. 한글 한 글자의 바이트가 두 조각에 걸쳐도 맞다.
  - 머리 `content-length: 2\r\nContent-Type: application/vscode-jsonrpc; charset=utf-8\r\n\r\n{}` 를 읽는다(Review Focus 3).
  - `ndjson`: `"{}\n{}\n"` 은 두 번, `"{}\r\n"` 은 `"{}"` 한 번, 빈 줄은 알리지 않는다. `encode("ndjson", "{}")` 는 `"{}\n"`.
- [ ] **Step 2: 돌려 실패를 본다** — `pnpm vitest run src/rpc/framing.test.ts`
- [ ] **Step 3: 구현한다.** 받은 조각을 `Buffer` 로 쌓는다. 길이 머리는 `\r\n\r\n` 까지를 머리로 읽고 `Content-Length` 를 대소문자 없이 찾는다. 머리에 길이가 없으면 그 머리를 버리고 다음을 읽는다.
- [ ] **Step 4: 돌려 통과를 본다**
- [ ] **Step 5: 커밋한다** — `feat(rpc): 메시지를 자르는 틀 둘(content-length · ndjson)`

### Task 2: 통로 — `stdio` 와 `websocket`

**Files:**
- Create: `src/rpc/transport.ts`
- Test: `src/rpc/transport.test.ts`

**Interfaces:**
- Consumes: Task 1 의 `createReader`, `encode`, `Framing`
- Produces:
  - 스펙 §6.2 통로를 여는 도우미의 `Transport` 꼴 그대로: `send(message: string): void`, `onMessage(fn)`, `onClose(fn: (reason?: Error) => void)`, `close(): void`. `onClose` 는 한 번만 알린다. `close()` 를 부른 뒤에도 알린다.
  - `stdio(child: { stdin: Writable; stdout: Readable; kill?(): unknown; on?(event: "exit", fn: () => void): unknown }, options: { framing: Framing; killAfter?: number }): Transport`
  - `websocket(url: string, options?: { headers?: Record<string, string>; maxPayload?: number }): Transport` — `ws` 를 동적 import 하지 않고 정적으로 가져온다(이 파일은 서버 전용). 연결이 열리기 전에 보낸 메시지는 열린 뒤 보낸다.

- [ ] **Step 1: 시험을 쓴다**
  - `stdio`: `PassThrough` 둘로 지은 가짜 프로세스에 보낸 글자가 틀대로 써지고, 써 넣은 메시지가 `onMessage` 로 온다.
  - 출력 흐름이 `end` 되면 `onClose` 가 한 번 온다. `exit` 이벤트에도 한 번만 온다.
  - `close()` 는 표준 입력을 닫는다. `kill` 이 있는 가짜는 `killAfter` 안에 `exit` 이 없으면 `kill` 이 한 번 불리고, 그 안에 `exit` 이 오면 불리지 않는다(가짜 타이머).
  - `websocket`: `ws` 의 `WebSocketServer` 를 띄워 오가는 메시지를 확인한다. `headers` 가 서버의 요청 머리에 닿는다. `maxPayload` 를 넘는 메시지가 오면 `onClose` 가 온다.
  - 서버가 pong 을 돌려주지 않으면(`autoPong: false`) `TIMING` 으로 줄인 끊김 판정 시간 뒤에 `onClose` 가 온다.
- [ ] **Step 2: 돌려 실패를 본다**
- [ ] **Step 3: 구현한다.** 웹소켓은 `pingMs` 마다 `ws.ping()`, 마지막 `pong` · 메시지에서 `idleMs` 가 지나면 `terminate()`.
- [ ] **Step 4: 돌려 통과를 본다**
- [ ] **Step 5: 커밋한다** — `feat(rpc): stdio · websocket 통로`

### Task 3: 세션 — 통로 하나 위의 JSON-RPC

**Files:**
- Create: `src/rpc/session.ts`, `src/rpc/error.ts`
- Test: `src/rpc/session.test.ts`

**Interfaces:**
- Consumes: Task 2 의 `Transport`
- Produces:
  - `class RpcError extends Error { requestId: number; code?: number; data?: unknown }` (`error.ts`). 0.3 의 `CommandError` 처럼 `message` 가 문구다.
  - `openSession(t: Transport, o: { handlers?: Record<string, (params: any) => unknown>; onNotification(n: { method: string; params?: unknown }): void; onClose(): void }): Session`
  - `interface Session { request(method: string, params: unknown, timeout: number, cancel?: (id: number) => { method: string; params?: unknown }): Promise<unknown>; notify(method: string, params?: unknown): void; close(): void }`
  - 요청 id 는 세션마다 1부터 오르는 정수. 통로가 닫히면 기다리던 요청은 모두 `RpcError(TEXT.unknown)` 로 끝나고 `onClose` 를 한 번 부른다. `close()` 로 닫으면 `TEXT.commandFailed` 로 끝난다.

- [ ] **Step 1: 시험을 쓴다** (가짜 `Transport`: 보낸 것을 배열에 담고, 받기를 손으로 넣는다)
  - 요청이 `{"jsonrpc":"2.0","id":1,"method":"m","params":{"a":1}}` 로 나가고, 같은 id 의 `result` 로 풀린다.
  - `error` 답은 `RpcError` 로 거절되고 `message` · `code` · `data` · `requestId` 가 상대의 것이다.
  - 제한 시간이 지나면 `RpcError("응답 지연")`, `cancel` 이 있으면 그 알림이 나간다. 그 뒤 온 답과 모르는 id 의 답은 버리고 던지지 않는다(Review Focus 4).
  - 통로가 닫히면 기다리던 요청이 `"연결 끊김. 알 수 없음"`, `close()` 면 `"연결 끊김. 명령 실패"`.
  - 상대의 요청: handler 의 값(Promise 도)으로 `result` 를 답한다. `undefined` 면 `result: null`(Review Focus 5). params 는 펼치지 않고 하나로 받는다. 던지면 `{"code":-32603,"message":<던진 문구>}`, 없으면 `{"code":-32601,"message":"Method not found"}`.
  - 알림은 `onNotification` 으로 간다. 배열 메시지는 하나씩 푼다. JSON 이 아닌 글자는 버리고 통로를 닫지 않는다.
  - `notify` 는 `id` 없이 나간다. params 를 주지 않으면 `params` 칸이 없다.
- [ ] **Step 2: 돌려 실패를 본다**
- [ ] **Step 3: 구현한다**
- [ ] **Step 4: 돌려 통과를 본다**

### Task 4: `createJsonRpc` — 생명주기 · 준비 문 · 다시 잇기 · 값

**Files:**
- Create: `src/rpc/client.ts`
- Test: `src/rpc/client.test.ts`

**Interfaces:**
- Consumes: Task 2 `Transport`, Task 3 `openSession` · `Session` · `RpcError`, `src/index.ts` 의 `DISPOSE`, `src/stream/protocol.ts` 의 `TEXT` · `DEFAULTS`, `src/stream/client.ts` 의 `TIMING` 꼴(같은 심볼을 쓰거나 같은 꼴의 심볼을 이 파일에 둔다)
- Produces:
  - `createJsonRpc<V, N extends { method: string; params?: unknown } = never, Cmd extends Record<string, (params: any) => unknown> = {}>, Names extends string = never>(o: JsonRpcOptions<V, N, Cmd, Names>): JsonRpc<V, Cmd, Names>` — `Names` 는 `notifications` 의 이름들로 추론한다
  - 옵션 칸은 스펙 §6.1 칸마다의 뜻 그대로: `connect: () => Transport | Promise<Transport>`, `onConnect?(last: V | undefined, rpc: { request(method, params?): Promise<unknown>; notify(method, params?): void }): V | Promise<V>`, `reduce?`, `requests`(이름마다 `{ method: string; timeout?: number }`), `notifications?`(이름마다 method), `handlers?`, `cancel?`, `timeout?`
  - 돌려주는 객체: 요청 이름마다 `(params) => Promise<결과>`, 알림 이름마다 `(params) => boolean`, `request(method, params?)`, `notify(method, params?): boolean`, `view(): ClientView<V>`(0.3 의 타입을 가져다 쓴다), `subscribe(fn): () => void`, `close(): void`, `[DISPOSE](): void`

- [ ] **Step 1: 시험을 쓴다** (가짜 통로를 `connect` 마다 새로 짓는다. `TIMING` 으로 다시 잇기 간격을 줄인다)
  - 상태 표(스펙 §7.2 연결 상태): 처음엔 `{ data: undefined, status: "loading", isFetching: true, error: null }`. `onConnect` 가 끝나면 `ready` · `isFetching: false` 이고 `data` 가 돌려준 값. 통로가 닫히면 `ready` · `isFetching: true` · `error: "연결 끊김. 재시도 중.."` 에 마지막 값 그대로. 다시 준비되면 `error: null`. `view()` 는 바뀌지 않았으면 같은 객체.
  - `onConnect` 를 주지 않으면 통로가 열리자마자 준비되고, `data` 는 처음엔 `undefined`.
  - 준비 전에 부른 요청은 `onConnect` 뒤에 부른 순서대로 나간다. 제한 시간은 부른 때부터 센다(준비를 기다리다 시간이 지나면 `"응답 지연"`, 상대에게 나가지 않는다).
  - `onConnect` 안의 `rpc.request` 는 기다리지 않고 곧바로 나간다. 다시 이을 때 `onConnect` 는 `last` 로 마지막 값을 받는다.
  - 준비 전에 부른 알림은 처음 열 때와 다시 이을 때 모두 나가지 않고 `false`. 준비된 뒤엔 `true` 이고, 알림과 요청이 부른 순서대로 나간다.
  - `onConnect` 도중 온 알림은 돌려준 값 위에 받은 순서대로 `reduce` 된다.
  - 통로가 닫히면 간격대로 `connect` 를 다시 부른다. `connect` 가 던지면 그 문구가 `error` 에 실리고 같은 간격으로 다시 부른다.
  - `onConnect` 안에서 보낸 요청 뒤 통로가 닫히면 그 요청은 `"연결 끊김. 알 수 없음"` 으로 끝나고, 다시 잇는다(Review Focus 1).
  - `close()` 뒤에는 `connect` 가 다시 불리지 않는다. 다시 잇기를 기다리는 중 · `onConnect` 도중에 불러도 같고, 열린 통로는 닫힌다(Review Focus 2). 기다리던 요청은 `"연결 끊김. 명령 실패"`. 상태는 `ready` · `isFetching: false` · `error: null` 에 마지막 값.
  - `createStore("x", () => createJsonRpc({...}))` 를 `resetStores()` 로 다시 지으면 앞 통로가 닫히고 새 통로가 열린다. `disposeStores()` 는 닫기만 한다.
  - 타입(`@ts-expect-error`): 셋째 타입 인자의 이름에 `requests` 칸이 없으면 오류, `requests` 에 `close` 같은 정해진 이름을 쓰면 오류, 인자가 둘인 요청 함수 타입이면 오류.
- [ ] **Step 2: 돌려 실패를 본다**
- [ ] **Step 3: 구현한다.** 준비 문은 「아직 준비 안 됨」 동안 요청을 대기열에 쥐고, 준비되면 부른 순서대로 지금 세션에 보낸다. 대기열의 요청마다 부른 때부터 제한 시간 타이머를 건다. 다시 잇기 간격은 0.3 `client.ts` 의 `backoff` 와 같은 식이고 준비되면 처음으로 되돌린다.
- [ ] **Step 4: 돌려 통과를 본다**
- [ ] **Step 5: 커밋한다** — `feat(rpc): createJsonRpc — 준비 문 · onConnect · 다시 잇기`
