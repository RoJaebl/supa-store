# supa-store 0.4 — 우리 약속을 모르는 JSON-RPC 상대를 store 로 꺼낸다 (설계 초안)

- 날짜: 2026-10-26
- 상태: **초안.** 0.3 설계에서 떼어 냈다(2026-10-26 사람이 정했다 — `createJsonRpc` 는 0.4 로 나눈다). 0.3 이 승인 · 구현된 뒤
  다시 읽고 검토를 거친다.
- 앞선 설계: 같은 폴더 `2026-10-25-supa-store-0.3-stream-design.md` — 생명주기(§6), `[DISPOSE]`, 연결 상태 표(§8.3), 문구(§8.4),
  다시 잇기 간격(§7.5)을 그대로 쓴다

## 1. 까닭

SSE · 웹소켓은 서버와 클라이언트를 한 주체가 지으므로, 서버가 supa-store 의 약속을 따르고 클라이언트만 맞추면 된다. JSON-RPC 는
상대가 다른 주체일 수 있다. 언어 서버(LSP)가 그렇고, 서버가 다른 서버와 이야기하는 경우도 있다. 그 상대는 supa-store 의 약속을
모르므로 0.3 의 약속만으로는 붙을 수 없다. 그래서 JSON-RPC 2.0 을 그대로 말하는 도우미를 따로 둔다.

0.3 은 같은 판단의 다른 갈래(우리 약속에 「서버가 클라이언트에 묻는 요청」을 더하는 것, 0.3 §7.6)를 담는다.

## 2. `createJsonRpc`

### 2.1 무엇을 하나

JSON-RPC 2.0 을 그대로 말한다. 언어 서버처럼 이미 JSON-RPC 를 말하는 상대에 중간 서버 없이 붙는다. store 로 꺼내는 틀과 생명주기는
0.3 의 `createStream` 과 같고, 상대가 모르는 우리 약속(버전 · 짧은 기록 · 답 기록 · 채널)은 듣지 않는다.

### 2.2 도는 자리와 연결

| 자리 | 붙는 상대 | 전송 |
|---|---|---|
| 서버(Node) | 서버 앱이 띄운 프로세스 | 표준 입출력. LSP 의 `Content-Length` 머리 꼴로 나눈다 |
| 서버(Node) | 다른 서버 | 웹소켓(`ws`) |
| 브라우저 | JSON-RPC 를 말하는 서버 | 웹소켓 |

프로세스나 연결은 앱이 열어 넘긴다. supa-store 는 요청 · 답 짝 맞추기, 알림, 제한 시간, 닫기만 맡는다. 프로세스의 일생은 앱에 남는다.

```ts
import { createJsonRpc } from "supa-store/rpc";

createStore("infra.lsp", (set, get, ctx) =>
  createJsonRpc({
    connect: () => {                                   // 열 때와 다시 이을 때 부른다
      const child = ctx("infra.lspProcess").spawn();   // 앱이 프로세스를 띄운다
      return { kind: "stdio", input: child.stdout, output: child.stdin };   // 또는 { kind: "ws", url }
    },
    initial: { diagnostics: {} as Record<string, Diagnostic[]> },
    reduce: (value, n) =>
      n.method === "textDocument/publishDiagnostics"
        ? { diagnostics: { ...value.diagnostics, [n.params.uri]: n.params.diagnostics } }
        : value,
    requests: { complete: "textDocument/completion", definition: "textDocument/definition" },
    notifications: { didOpen: "textDocument/didOpen", didChange: "textDocument/didChange" },
    handlers: { "workspace/applyEdit": async (edit) => ({ applied: await applyEdit(edit) }) },
    onReconnect: async (last, rpc) => {
      for (const uri of openFiles()) await rpc.notify("textDocument/didOpen", { textDocument: docOf(uri) });
      return last;
    },
    timeout: 30_000,
  }),
);
```

### 2.3 값과 상태

- `data`: `initial` 에서 시작해 알림을 `reduce` 로 합친 값.
- `requests` 의 이름마다 `MutationView`. `notifications` 의 이름마다 답을 기다리지 않는 함수.
- 연결 상태는 0.3 설계 §8.3 의 표와 같다. 다시 이어도 마지막 값으로 이어 간다. 상대와 다시 맞추는 일은 `onReconnect(last, rpc)` 에서 쓰는 쪽이
  한다. 주지 않으면 마지막 값을 그대로 이어 간다. 비우려면 `initial` 을 돌려준다.
- 보낸 뒤 끊긴 요청은 곧바로 「연결 끊김. 알 수 없음」으로 끝난다. 끊긴 동안 부른 요청은 「연결 끊김. 명령 실패」, 제한 시간이 지나면
  「응답 지연」이다.
- 표준 입출력 상대는 「다시 잇기」가 곧 `connect` 를 다시 부르는 것이다. 프로세스가 끝나 입력이 닫히면 끊긴 것으로 보고 0.3 설계 §7.5 의
  간격으로 `connect` 를 다시 부른다. 다시 띄울지는 앱의 `connect` 가 정한다.

### 2.4 서버에서 쓸 때

`createJsonRpc` 는 React 없이도 돈다. 서버 코드는 `createStore` 없이 `createJsonRpc(...)` 의 돌려준 객체를 바로 쓴다(`rpc.request` ·
`rpc.notify` · `rpc.on(method, fn)` · `rpc.close()`). 서버 앱이 언어 서버의 진단을 받아 `createStreamServer` 로 브라우저에 `publish`
하는 꼴이 이 자리다.

## 3. 하위 경로와 의존

| 하위 경로 | 담는 것 | 도는 자리 | 의존 |
|---|---|---|---|
| `supa-store/rpc` | `createJsonRpc` | 브라우저 · Node | 없다(Node 의 웹소켓은 `ws`, 선택 peer) |

## 4. 시험

- 가짜 JSON-RPC 상대를 표준 입출력 쌍(`PassThrough` 둘)으로 붙여 시험한다.
- `onReconnect` 가 돌려준 값으로 이어 가고, 상대가 묻는 요청에 `handlers` 가 답한다.

## 5. Claude 가 정한 것 — 사람이 확인할 것

1. **표준 입출력은 LSP 의 `Content-Length` 머리 꼴로 나눈다.** 언어 서버가 쓰는 꼴이고, JSON-RPC 표준 자체는 나누는 법을 정하지 않는다.
2. **`createJsonRpc` 는 환경을 가리지 않고 지어질 때 연다.** 서버에서도 쓰는 도우미이기 때문이다. 정의 파일이 서버에서 평가되더라도
   store 는 처음 꺼낼 때 지어지므로, 꺼내지 않으면 열리지 않는다. store 없이 바로 쓸 때는 `createJsonRpc(...)` 를 부르는 순간 연다.

## 6. 나중에 고려할 것

- **store 를 서버용으로 빌드하는 기능**(사람이 남겼다). store 의 서버 서비스와 따로, store 를 서버용으로 빌드해 「서버에서도 도는
  JSON-RPC 클라이언트」를 그것으로 내는 길. 지금은 §2.4 처럼 `createJsonRpc` 를 React 없이 바로 쓴다.
