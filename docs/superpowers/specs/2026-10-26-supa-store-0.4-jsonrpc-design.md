# supa-store 0.4 — 서버 앱이 JSON-RPC 상대와 이야기하는 연결을 store 로 꺼낸다

- 날짜: 2026-10-26 (초안), 2026-10-27 다시 씀
- 상태: **승인됨 — 0.4.0 으로 구현**
- 앞선 설계: 같은 폴더 `2026-10-25-supa-store-0.3-stream-design.md`. 아래에서 「0.3 §n」은 그 문서의 절이다.
  생명주기(§6 생명주기), 다시 잇기 간격(§7.5 heartbeat 와 다시 잇기), 연결 상태 표(§8.3 연결 상태), 문구(§8.4 문구)를 이어 쓴다.

## 1. 의도

0.3 의 `createStream` 은 우리가 짓는 서버(홉)와만 이야기한다. 서버와 클라이언트가 같은 약속을 따르기 때문이다. 그런데 서버 앱은
우리 약속을 모르는 상대와도 이야기해야 한다.

- 서버 앱이 띄운 언어 서버(LSP), MCP 서버, 그 밖의 개발 도구 프로세스. 표준 입출력으로 JSON-RPC 를 말한다.
- JSON-RPC 를 말하는 다른 서버. 웹소켓으로 붙는다.

이런 상대와 이야기하려면 요청 id 짝 맞추기, 알림 받기, 상대가 묻는 요청에 답하기, 제한 시간, 끊김과 다시 잇기, 메시지 자르기를
누군가 짜야 한다. 0.4 는 그것을 맡고, 그 결과를 0.3 과 같은 틀(값, 상태, 명령, 생명주기)로 꺼낸다.

브라우저는 0.4 를 쓰지 않는다. 브라우저가 이 값을 보려면 서버 앱이 0.4 로 받은 값을 0.3 의 `createStreamServer` 로 `publish` 하고,
브라우저가 `createStream` 으로 받는다.

```text
JSON-RPC 상대(언어 서버, 다른 서버)
   │  0.4 createJsonRpc
   ▼
서버 앱 ── 0.3 createStreamServer.publish ──▶ 브라우저(0.3 createStream)
```

## 2. 목표

- 서버 앱이 JSON-RPC 2.0 상대에 표준 입출력이나 웹소켓으로 붙는다.
- 요청은 이름이 붙은 함수로 부르고, 타입은 0.3 처럼 타입 인자로 적는다.
- 상대의 알림은 `reduce` 로 하나의 값에 쌓인다.
- 상대가 묻는 요청에 `handlers` 가 답한다.
- 상대가 죽거나 끊기면 다시 잇고, 이을 때마다 `onConnect` 가 상대와 맞춘다.
- 준비되기 전에 부른 요청은 준비될 때까지 기다린다. 제한 시간이 그 기다림을 막는다.
- 같은 객체를 `createStore` 안에서도 쓰고, store 없이 바로도 쓴다.

## 3. 하지 않는 것

- **JSON-RPC 가 아닌 약속.** gRPC, tRPC, MessagePack-RPC 같은 것은 다루지 않는다. 묻고 답하기만 하는 약속은 0.2 의
  `createResource` 안에서 그 클라이언트를 부르면 된다.
- **브라우저에서 돌기.** 브라우저 자리는 0.3 이 맡는다(§1 의도).
- **우리가 일괄(배열) 요청을 보내기.** 받는 일괄은 푼다(§7.4 상대가 보낸 것을 읽기).
- **프로세스의 일생.** 프로세스를 띄우고 다시 띄울지는 앱의 `connect` 가 정한다. 0.4 는 받은 통로만 다룬다.

## 4. 실패로 보는 것

- 상대가 다시 떴는데 맞춤(`initialize` 같은 것)이 빠져 상대가 요청을 거절한다.
- 서버 앱이 뜨는 동안 들어온 요청이 「준비 전」이라는 까닭만으로 실패한다.
- 끊긴 뒤 보낸 요청이 결과를 모른 채 영원히 기다린다.
- 개발 서버가 코드를 다시 읽을 때 언어 서버 프로세스가 겹쳐 뜬다.
- 큰 메시지(완성 목록, 문서)가 크기 한도에 걸려 잘린다.
- 쓰는 쪽이 0.3 과 다른 칸 이름이나 상태 표를 따로 외워야 한다.

## 5. 고려한 길

| 길 | 이 길이 담는 범위 | 버린 까닭 또는 고른 까닭 |
|---|---|---|
| 약속 · 틀 · 전송 세 층을 모두 갈아 끼우게 연다 | JSON-RPC 가 아닌 약속까지 | 열린 연결 위에서 양쪽이 말을 거는 상대는 거의 JSON-RPC 다. 그 밖의 약속은 자기 클라이언트가 이미 있다. 시험하고 설명할 것만 커져 버렸다 |
| **JSON-RPC 하나만 말하고, 틀과 전송만 고르게 한다** | 언어 서버, MCP, JSON-RPC 서버 | **골랐다.** 실제 상대를 다 덮는다. 세 층으로 나눠 지어 두면 나중에 약속 층을 안을 바꾸지 않고 열 수 있다 |
| 0.3 의 `createStream` 에 JSON-RPC 모드를 더한다 | 같은 함수 하나 | 0.3 은 버전, 짧은 기록, 답 기록 위에 서 있어 동작이 다르다. 한 함수에 두 동작을 섞으면 두 쪽 규칙이 서로 새어 든다 |

## 6. 정의

```ts
import { createJsonRpc, stdio } from "supa-store/rpc";

type Note = { method: "textDocument/publishDiagnostics"; params: PublishDiagnosticsParams };
type Cmd = {
  complete: (p: CompletionParams) => CompletionList;
  definition: (p: DefinitionParams) => Location[];
};

createStore("infra.lsp", (set, get, ctx) =>
  createJsonRpc<{ diagnostics: Record<string, Diagnostic[]> }, Note, Cmd, { didChange: DidChangeTextDocumentParams }>({
    connect: () => stdio(spawn("typescript-language-server", ["--stdio"]), { framing: "content-length" }),
    onConnect: async (last, rpc) => {
      await rpc.request("initialize", { processId: process.pid, rootUri, capabilities: {} });
      rpc.notify("initialized", {});
      for (const doc of openDocs()) rpc.notify("textDocument/didOpen", { textDocument: doc });   // 처음이든 다시든 지금 문서를 보낸다
      return last ?? { diagnostics: {} };
    },
    reduce: (value, n) => ({ diagnostics: { ...value.diagnostics, [n.params.uri]: n.params.diagnostics } }),
    requests: {
      complete: { method: "textDocument/completion", timeout: 5_000 },
      definition: { method: "textDocument/definition" },
    },
    notifications: { didChange: "textDocument/didChange" },
    handlers: { "workspace/configuration": () => [{}] },
    cancel: (id) => ({ method: "$/cancelRequest", params: { id } }),
  }),
);
```

### 6.1 칸마다의 뜻

| 칸 | 담는 것 | 생략하면 |
|---|---|---|
| 첫째 타입 인자 | 쌓인 값의 타입 | — |
| 둘째 타입 인자 | 상대가 보내는 알림의 타입. `{ method, params }` 의 합 | 알림을 받지 않는다 |
| 셋째 타입 인자 | 요청 이름마다의 함수 타입. 0.3 의 셋째 타입 인자와 같은 꼴 | 요청이 없다 |
| 넷째 타입 인자 | 보낼 알림 이름마다의 params 타입. 0.3 의 셋째 타입 인자와 같은 꼴 | 알림 이름 함수가 없다 |
| `connect` | 통로를 여는 함수. 처음 열 때와 다시 이을 때마다 부른다 | 생략할 수 없다 |
| `onConnect(last, rpc)` | 통로가 열린 뒤 상대와 맞추고, 이어 갈 값을 돌려준다. 처음 열 때 `last` 는 `undefined` | 맞춤 없이 곧바로 준비되고, 값은 마지막 값 그대로다. 처음이면 `undefined` 다 |
| `reduce(value, note)` | 알림 하나를 값에 합친다 | 알림이 값을 바꾸지 않는다 |
| `requests` | 요청 이름마다 `{ method, timeout? }`. 셋째 타입 인자의 이름마다 한 칸이 있어야 한다(없으면 타입 오류) | 요청이 없다 |
| `notifications` | 넷째 타입 인자의 이름마다 method. 한 칸이 있어야 한다(없으면 타입 오류) | 이름 붙은 알림 함수가 없다. `notify(method, params)` 는 그대로 쓸 수 있다 |
| `handlers` | 상대가 묻는 요청의 method 마다 답하는 함수. 상대의 `params` 를 하나로 받는다(§8 꺼내는 두 꼴) | 상대가 묻는 요청에 `-32601 Method not found` 로 답한다 |
| `cancel(id)` | 「응답 지연」으로 끝낸 요청을 상대에게 알리는 알림을 짓는다 | 상대에게 알리지 않는다 |
| `timeout` | 요청을 기다리는 기본 시간 | 30초(0.3 과 같다) |

`onConnect` 에 넘어오는 `rpc` 는 준비 문을 거치지 않는다. 그 안의 `rpc.request` 는 곧바로 보내진다(그래야 맞춤이 끝날 수 있다).
`rpc.request(method, params)` 와 `rpc.notify(method, params)` 는 method 를 그대로 받는다.

### 6.2 통로를 여는 도우미

| 도우미 | 붙는 상대 | 메시지를 자르는 법 |
|---|---|---|
| `stdio(child, { framing, killAfter? })` | 표준 입출력을 가진 프로세스. `{ stdin, stdout }` 을 가진 것이면 된다. `on?("close" | "error", fn)` 을 가진 것(`ChildProcess`)을 넘기면 `close`(표준 입출력이 다 닫힌 뒤)를 프로세스의 끝남으로, `error` 를 그 까닭으로 본다 | `framing: "content-length"` 는 LSP 의 길이 머리, `"ndjson"` 은 한 줄에 메시지 하나(MCP) |
| `websocket(url, { headers?, maxPayload? })` | JSON-RPC 를 말하는 웹소켓 서버. Node 의 `ws` 로 붙는다 | 프레임 하나가 메시지 하나 |

두 도우미는 같은 꼴의 통로 객체를 돌려준다. 이 꼴은 내보내므로 앱이 다른 통로(예: `MessagePort`, 다른 소켓)를 직접 지어 넘길 수 있다.

```ts
interface Transport {
  send(message: string): void;
  onMessage(fn: (message: string) => void): void;
  onClose(fn: (reason?: Error) => void): void;
  close(): void;
}
```

## 7. 동작

### 7.1 생명주기

0.3 §6 생명주기를 그대로 따르되 한 가지가 다르다.

- **지어질 때 연다.** 0.4 는 서버 앱에서만 돌므로, 0.3 처럼 서버에서 그릴 때 열지 않는 규칙(`open: "browser"`)이 없다. store 로 쓰면
  처음 꺼낼 때 지어지고, 바로 쓰면 `createJsonRpc(...)` 를 부르는 순간 연다.
- **다시 지을 때 닫는다.** `[DISPOSE]` 가 통로를 닫는다. `disposeStores()` 도 0.3 과 같다.
- **`stdio` 는 닫을 때 프로세스를 끝낸다.** 표준 입력을 닫고, 받은 것에 `kill()` 이 있으면 `killAfter`(기본 2초) 안에 스스로 끝나지
  않을 때 `kill()` 을 부른다. 입력이 끊겨도 스스로 끝나지 않는 서버가 있고, Windows 에서는 고아 프로세스가 잘 남기 때문이다. 그래서
  개발 서버가 정의 파일을 다시 읽어도 프로세스가 겹쳐 뜨지 않는다. 프로세스를 앱이 따로 거두려면 `{ stdin, stdout }` 만 넘긴다.

### 7.2 연결 상태

칸 이름과 표는 0.3 §8.3 연결 상태와 같다. 다른 점은 「준비」가 `onConnect` 가 끝난 때라는 것이다.

| 때 | `data` | `status` | `isFetching` | `error` |
|---|---|---|---|---|
| 처음 열거나 처음 `onConnect` 가 도는 중 | `undefined` | `loading` | `true` | `null` |
| 준비되어 알림을 받는 중 | 지금 값 | `ready` | `false` | `null` |
| 끊겨 다시 잇는 중(다시 이은 뒤 `onConnect` 가 도는 동안도) | 마지막 값 그대로 | `ready` | `true` | 연결 끊김. 재시도 중.. |
| `close()` 로 닫았다 | 마지막 값 그대로 | `ready` | `false` | `null` |

- 통로가 닫히거나 `onConnect` 가 던지면 끊긴 것으로 보고 0.3 §7.5 heartbeat 와 다시 잇기의 간격(1초에서 두 배씩, 30초에서 멈춤,
  ±20%)으로 `connect` 를 다시 부른다. 준비되면 1초로 되돌린다.
- 0.3 의 「다시 오지 마라」 닫기 신호는 상대가 모르므로 없다. 그래서 `status: "error"` 로 멈추는 때가 없다. 멈추려면 앱이
  `close()` 를 부른다. `connect` 가 던지면 그 오류의 문구를 `error` 에 싣고 같은 간격으로 다시 부른다.
- `onConnect` 가 도는 동안 받은 알림은 쥐고 있다가, `onConnect` 가 돌려준 값 위에 받은 순서대로 `reduce` 한다.

### 7.3 요청

- **준비 전에 부른 요청은 기다린다.** 처음 열 때, 끊겨 다시 잇는 동안, `onConnect` 가 도는 동안이 모두 「준비 전」이다. 준비되면
  부른 순서대로 보낸다. 제한 시간은 부른 때부터 센다. 0.3 은 같은 경우 곧바로 실패시키는데, 그것은 사람이 누른 버튼이 잠자코
  기다리지 않게 하려는 화면 쪽 사정이었다. 0.4 를 부르는 쪽은 서버 앱의 코드라, 상대가 다시 뜨는 몇 초를 기다리는 편이 낫다.
- **준비 전에 부른 알림은 버린다.** 처음 열 때든 다시 이을 때든 같다. 알림은 상대의 상태를 바꾸는데(`didOpen`, `didChange`),
  상대와 상태를 맞추는 일은 처음과 다시를 가리지 않고 `onConnect` 가 한다. 쌓아 두었다가 내보내면 `onConnect` 가 이미 맞춘 상태 위에
  한 번 더 고쳐져 어긋난다. 그래서 `onConnect` 는 `last` 가 있든 없든 지금 상태를 상대에게 보낸다(§6 정의의 `didOpen`). 버린 알림은
  알림 함수가 `false` 를 돌려 알린다. 보냈으면 `true` 다.
- **준비된 뒤의 요청과 알림은 부른 순서대로 나간다.** `didChange` 뒤에 부른 `completion` 이 그 바뀜을 본다.
- **보낸 뒤 끊긴 요청은 곧바로 「연결 끊김. 알 수 없음」으로 끝난다.** 상대에게 답 기록이 없으므로 다시 이어도 결과를 알 길이 없다.
- **제한 시간이 지나면 「응답 지연」으로 끝나고**, 이미 보낸 요청이고 `cancel` 이 있으면 그 알림을 상대에게 보낸다. 늦게 온 답은 버린다.
- **상대가 실패로 답하면** 상대의 `error.message` 를 그대로 문구로 쓴다. 오류 객체는 0.3 의 `CommandError` 처럼 `requestId` 를 갖고,
  JSON-RPC 의 `code` 와 `data` 를 더 갖는다(`RpcError`).

| 요청이 끝나는 까닭 | 문구 |
|---|---|
| 제한 시간 안에 답이 오지 않았다(준비를 기다린 시간도 센다) | 응답 지연 |
| 보낸 뒤 통로가 끊겼다 | 연결 끊김. 알 수 없음 |
| `close()` 로 닫았다(기다리던 요청과 보낸 요청 모두) | 연결 끊김. 명령 실패 |
| 상대가 `error` 로 답했다 | 상대의 `error.message` |

### 7.4 상대가 보낸 것을 읽기

- `id` 와 `result` 또는 `error` 가 있으면 우리 요청의 답이다.
- `method` 가 있고 `id` 가 없으면 알림이다. `reduce` 로 간다.
- `method` 와 `id` 가 함께 있으면 상대가 묻는 요청이다. `handlers[method]` 가 돌려준 값(또는 그 Promise 의 값)으로 답한다. 던지면
  `-32603 Internal error` 와 던진 문구로 답한다. 맞는 handler 가 없으면 `-32601 Method not found` 로 답한다. 상대가 묻는 요청은
  준비 전에도 답한다(언어 서버는 `initialize` 도중에도 묻는다).
- 배열이면 하나씩 풀어 위 규칙대로 읽는다.
- JSON 으로 읽히지 않는 메시지는 버리고 통로를 닫지 않는다.

### 7.5 크기 한도

- 표준 입출력에는 한도를 두지 않는다. 앱이 띄운 믿는 프로세스이고, 큰 완성 목록과 문서가 흔하다.
- 웹소켓은 `maxPayload` 기본 1 MiB 다(0.3 과 같다). 넘는 메시지가 오면 `ws` 가 통로를 닫고, 끊긴 것으로 다시 잇는다.

### 7.6 끊김을 알아채기

0.3 의 `ping` · `pong` 메시지는 상대가 모르는 우리 약속이라 쓰지 않는다.

- 표준 입출력: 출력 흐름이 끝나거나 프로세스가 끝나면 끊긴 것이다.
- 웹소켓: 웹소켓 표준의 ping 프레임을 25초마다 보내고, 60초 안에 pong 이 없으면 끊긴 것으로 본다. 값은 0.3 과 같다.

## 8. 꺼내는 두 꼴

`createJsonRpc` 가 돌려주는 객체 하나가 두 꼴로 다 쓰인다.

**store 로 꺼낸다.** 다른 store 는 `ctx` 로 부른다. 화면은 쓰지 않는다(§1 의도).

```ts
createStore("editor.complete", (set, get, ctx) => ({
  run: (p: CompletionParams) => ctx("infra.lsp").complete(p),
}));
```

**store 없이 바로 쓴다.**

```ts
const lsp = createJsonRpc<Value, Note, Cmd, Out>({ ... }); // Out: 위 정의의 알림 보내기 꼴(여기서는 { didChange: DidChangeTextDocumentParams })

app.post("/complete", async (req, res) => res.json(await lsp.complete(req.body)));
lsp.subscribe(() => hop.publish("lsp", lsp.view().data));   // 0.3 의 홉으로 브라우저에 보낸다
process.on("SIGTERM", () => lsp.close());
```

| 객체의 칸 | 하는 일 |
|---|---|
| 요청 이름마다의 함수 | 그 요청을 보내고 결과를 돌려준다. 실패하면 `RpcError` 를 던진다 |
| 알림 이름마다의 함수 | 그 알림을 보내고 `true` 를 돌려준다. 준비 전이면 버리고 `false` 를 돌려준다(§7.3 요청) |
| `request(method, params)` · `notify(method, params)` | 이름을 붙이지 않은 요청과 알림. 준비 전의 동작은 이름 붙은 함수와 같다 |
| `view()` · `subscribe(fn)` | §7.2 연결 상태의 값을 읽고, 바뀔 때 알린다. 바뀌지 않았으면 같은 객체 |
| `close()` | 통로를 닫고 다시 잇지 않는다 |
| `[DISPOSE]` | store 로 쓸 때 다시 짓기 직전에 닫는 표식. 0.3 과 같다 |

`request` · `notify` · `view` · `subscribe` · `close` 는 이름이 정해져 있으므로 `requests` · `notifications` 의 이름으로 쓸 수 없다(타입 오류).

**`[USE]` 는 두지 않는다.** 0.3 의 `[USE]` 는 React 훅이고, 0.4 는 화면이 쓰지 않으므로 React 를 들이지 않는다. 그래서 요청 칸마다의
상태(`MutationView`)와 `retry()` 도 없다. 서버 코드는 실패한 요청을 같은 함수로 다시 부른다.

**params 는 하나다.** JSON-RPC 의 `params` 는 객체 하나 또는 배열 하나다. 그래서 셋째 타입 인자의 함수는 인자를 하나만 받는다(둘
이상이면 타입 오류). 그 인자가 그대로 `params` 가 된다. `handlers` 도 상대의 `params` 를 펼치지 않고 하나로 받는다. 이 점이 0.3 의
`handlers`(배열을 펼쳐 받는다)와 다르다.

## 9. 하위 경로와 의존

| 하위 경로 | 담는 것 | 의존 |
|---|---|---|
| `supa-store/rpc` | `createJsonRpc`, `stdio`, `websocket`, `Transport`, `RpcError` | `ws`(선택 peer, `websocket` 을 쓸 때만). Node 20 이상 |

`supa-store/rpc` 는 React 를 들이지 않는다. 서버 앱 전용이므로 `exports` 에 `browser` 조건을 두지 않는다.

## 10. 시험

- 가짜 상대를 `PassThrough` 두 개로 짓고 `stdio` 에 붙인다. `content-length` 와 `ndjson` 두 틀 모두.
- 메시지가 여러 조각으로 나뉘어 오거나 두 메시지가 한 조각에 붙어 와도 틀이 바르게 자른다. 길이 머리는 바이트 수다(한글이 섞여도 맞다).
- 준비 전에 부른 요청이 `onConnect` 뒤에 부른 순서대로 나가고, 제한 시간은 부른 때부터 센다.
- `onConnect` 안의 `rpc.request` 는 기다리지 않고 곧바로 나간다.
- 준비 전에 부른 알림은 처음 열 때와 다시 이을 때 모두 나가지 않고 `false` 를 돌려준다. 준비된 뒤의 알림과 요청은 부른 순서대로 나간다.
- `onConnect` 도중에 온 알림이 돌려준 값 위에 순서대로 쌓인다.
- 보낸 뒤 끊기면 「알 수 없음」, 제한 시간이 지나면 「응답 지연」과 `cancel` 알림, `close()` 면 「명령 실패」.
- 프로세스가 끝나면 간격대로 `connect` 를 다시 부르고, `onConnect` 가 `last` 를 받는다.
- 상대가 묻는 요청: handler 가 답하고, 던지면 `-32603`, 없으면 `-32601`. 준비 전에도 답한다.
- 상대가 일괄로 보낸 메시지를 푼다. JSON 이 아닌 메시지는 버리고 통로를 닫지 않는다.
- `[DISPOSE]` 가 통로를 닫고, 다시 지은 store 가 새 통로를 연다.
- 웹소켓: `ws` 로 띄운 가짜 서버에 붙고, pong 이 없으면 끊긴 것으로 보고 다시 잇는다.
- 타입: 셋째 타입 인자의 이름마다 `requests` 칸이 없으면 오류, 정해진 이름(`request` 등)을 쓰면 오류.

## 11. 사람이 정한 것 (2026-10-26 · 27 대화)

- 0.4 는 JSON-RPC 2.0 하나만 말한다. 약속 층은 열지 않고 틀과 전송만 고르게 한다.
- 0.4 는 서버 앱 자리 둘(띄운 프로세스, 다른 서버)만 맡는다. 브라우저는 0.3 의 홉을 거친다.
- 처음 열 때와 다시 이을 때의 맞춤은 하나로 합쳐 `onConnect` 로 부른다.
- 준비 전에 부른 요청은 제한 시간 안에서 기다린다(0.3 과 다르다).
- store 로 꺼내는 꼴과 바로 쓰는 꼴을 둘 다 둔다.
- 준비 전에 부른 알림은 처음 열 때와 다시 이을 때를 가리지 않고 버린다. 상태를 맞추는 일은 `onConnect` 한 곳이 한다.
- store 꼴은 서버 전용 설정 · 등록부에서만 쓴다는 전제로 둔다. `store-gen` 의 생성 파일이 모든 정의 파일을 import 하므로, 화면과 같은
  등록부에 두면 `child_process` 가 브라우저 묶음에 들어간다. 그런 프로젝트는 store 없이 바로 쓰는 꼴을 쓴다. 나누는 기능은 나중에
  다룬다(§13 나중에 고려할 것).
- 0.4 는 독립 스펙으로 쓴다. 남의 라이브러리가 흘려보내는 값을 꺼내는 도우미는 `createFeed` 라는 이름으로 나중에 생각한다
  (§13 나중에 고려할 것).

## 12. Claude 가 정한 것 — 사람이 확인할 것

1. **명령을 적는 꼴은 0.3 에 맞췄다.** 타입은 셋째 타입 인자, `requests` 에는 이름마다 `{ method, timeout? }`.
2. **`[USE]` · 요청 칸의 상태 · `retry()` 를 두지 않는다**(§8 꺼내는 두 꼴). 화면이 쓰지 않으므로 React 를 들이지 않는다.
   빌더 검토가 짚었다.
3. **취소는 선택 칸 `cancel` 로 둔다.** JSON-RPC 표준에는 취소가 없고, LSP 의 `$/cancelRequest` 는 그 칸으로 적는다.
4. **크기 한도는 표준 입출력에 없고, 웹소켓은 1 MiB 다**(§7.5 크기 한도).
5. **상대의 실패는 `RpcError` 로 던진다.** `message` 는 상대의 문구, 그리고 `requestId` · `code` · `data`.
6. **맞는 handler 가 없으면 `-32601`, handler 가 던지면 `-32603` 로 답한다.** 둘 다 JSON-RPC 표준의 코드다.
7. **상대가 보낸 일괄은 풀고, 우리는 일괄로 보내지 않는다.**
8. **`onConnect` 도중에 온 알림은 쥐었다가 돌려준 값 위에 쌓는다**(§7.2 연결 상태). 버리면 언어 서버가 `initialize` 직후 보낸
   진단을 잃는다.
9. **`status: "error"` 로 멈추는 때가 없다.** 상대가 「다시 오지 마라」를 말할 길이 없어서다. `connect` 가 던지면 `error` 에 그 문구를
   싣고 계속 다시 부른다.
10. **웹소켓의 끊김은 웹소켓 표준의 ping 프레임으로 알아챈다.** 값(25초, 60초)은 0.3 과 같다.
11. **`stdio` 는 `{ stdin, stdout }` 을 가진 것이면 받는다.** 소켓처럼 양쪽 흐름이 하나인 것을 붙이려면 앱이 `Transport` 를 직접 짓는다.
12. **`close()` 뒤의 `status` 는 `ready` 이고 `error` 는 비어 있다.** 앱이 스스로 닫은 것이라 실패로 보이지 않는다.
13. **params 는 하나다.** 요청 함수는 인자 하나를 받아 그대로 `params` 로 보내고, `handlers` 는 `params` 를 펼치지 않고 받는다.
    LSP 처럼 객체 하나를 쓰는 상대에서 0.3 의 펼쳐 받기가 깨지기 때문이다. 빌더 검토가 짚었다.
14. **`stdio` 는 닫을 때 프로세스를 끝낸다**(§7.1 생명주기). 기본 유예 2초. 빌더 검토가 짚었다.
15. **보낼 알림의 타입은 넷째 타입 인자로 받는다.** 빌더 검토가 짚었다.

## 13. 나중에 고려할 것

- **`createFeed`.** tRPC 구독이나 gRPC 서버 스트리밍처럼, 남의 클라이언트 라이브러리가 이미 연 구독이나 async iterator 를 받아
  값 · 상태 · 생명주기만 store 틀에 맞추는 작은 도우미. 연결도 약속도 맡지 않는다. 지금 쓸 소비자가 없어 미룬다.

  ```ts
  createStore("users.live", () =>
    createFeed({
      source: () => client.watchUsers({}),   // 또는 subscribe: (push, fail) => () => unsubscribe()
      initial: [] as UserEvent[],
      reduce: (list, ev) => [...list, ev],
    }),
  );
  ```

- **JSON-RPC 가 아닌 약속.** 필요해지면 약속 층(메시지를 읽고 짓는 객체)을 연다. 틀 · 전송과 따로 지어 두므로 안을 바꾸지 않는다.
- **store 를 서버용으로 빌드하는 기능.** store 의 서버 서비스와 따로, store 를 서버용으로 빌드하는 길(2026-10-26 사람이 남겼다).
  서버 등록부와 화면 등록부를 나눠 생성하면 0.4 의 store 꼴을 화면과 같은 프로젝트에서도 쓸 수 있다(§11 사람이 정한 것의 전제를
  푸는 자리).
