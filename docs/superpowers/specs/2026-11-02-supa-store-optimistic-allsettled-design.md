# supa-store 0.5 보완 — 밀려난 호출은 겹에서 빠지고(`optimistic`), 모든 호출이 끝나면 한 번 확인한다(`onAllSettled`)

- 날짜: 2026-11-02
- 바탕: [0.5 설계](./2026-10-30-supa-store-mutation-state-design.md) — 이 문서는 그 설계를 고친다. 고치지 않은 것은 그 문서를 따른다
- 브랜치: `mutation-state+` (dev `4bac257` 을 되받은 `b10a210` 위)

## 1. 의도와 까닭

0.5 를 dev 에 올린 뒤 대화와 견주어 다시 읽었더니 셋이 어긋나 있었다.

- **늦은 응답을 가리는 기준이 틀렸다.** 지금은 「더 나중 번호가 끝났으면」 앞 호출의 응답을 버린다. 그런데 나중 호출이
  **실패**해도 앞 호출을 버린다. 나중 호출이 실패했으면 서버의 값은 앞 호출이 만든 값이므로, 앞 호출의 `onSuccess` 가 캐시에
  그 값을 적어야 한다.
- **겹이 늦은 호출을 그대로 얹는다.** 앞 호출이 늦게 끝날 때까지 `inflight` 에 남아 있으므로, `inflight` 를 겹으로 쓰면 나중
  호출이 이미 성공해 캐시가 서버 값이 된 뒤에도 앞 호출의 인자가 그 위에 얹힌다.
- **서버가 받은 차례대로 처리한다는 전제를 대신할 길이 없다.** 0.5 설계 §2.4 는 그렇지 않은 서버에 `scope` 를 쓰라고 했다.
  하지만 줄을 세우면 빠른 연속 입력이 느려진다. 동시에 보내면서도 마지막에 서버와 맞출 길이 필요하다.

`inflight` · `pending` 의 뜻은 바꾸지 않는다. 둘은 **아직 오가는 요청**을 글자 그대로 말하고, 버튼의 잠금이나 줄마다의 도는
표시가 그 뜻에 기댄다. 겹에 쓸 목록은 따로 둔다.

## 2. 정한 것

### 2.1 밀려남 — 나중에 보낸 호출이 성공하면 앞 호출은 모두 밀려난다

- 호출 n 이 **성공**하면 n 보다 앞서 보낸 호출은 모두 **밀려난다.**
- 밀려난 호출의 응답은 `data` · `error` 를 고치지 않고 `onSuccess` · `onError` · `onSettled` 를 부르지 않는다. 그 호출의
  `mutateAsync` 는 자기 결과로 끝난다(0.5 와 같다).
- **나중 호출의 실패는 아무것도 밀어내지 않는다.** 실패한 호출은 서버의 값을 바꾸지 않았다고 보기 때문이다.
- 밀려난 호출도 응답이 올 때까지 `inflight` 에 남는다. 요청은 실제로 아직 오가는 중이기 때문이다.

0.5 의 「더 나중 번호가 끝났으면 늦은 응답」을 이것으로 바꾼다. 늦은 응답이라는 말 대신 **밀려남**을 쓴다.

**`error` 와 `data` 는 「마지막으로 끝난, 밀려나지 않은 호출」을 따른다.** 빨강을 보내고 초록을 보냈는데 초록이 먼저 실패하고
빨강이 나중에 성공하면, `error` 는 초록의 문구였다가 `null` 이 되고 `data` 는 빨강의 결과가 된다. 서버의 값이 빨강이기
때문이다.

### 2.2 `optimistic` — 겹에 얹을 호출들

상태 칸에 `optimistic` 을 더한다.

| 칸 | 담는 것 |
|---|---|
| `inflight` | 보냈지만 응답이 아직 오지 않은 호출들의 인자. 0.5 와 같다 |
| `pending` | `inflight.length > 0`. 0.5 와 같다 |
| `optimistic` | 겹에 얹을 호출들의 인자. 보낸 차례대로 선다. `inflight` 에서 밀려난 호출을 뺀 것이고, `onAllSettled` 를 적었으면 확인을 기다리는 호출을 더한 것이다(§2.3) |
| `error` · `data` | 0.5 와 같다. 기준만 §2.1 을 따른다 |

- 밀려난 호출은 밀려나는 그 순간 `optimistic` 에서 빠진다. 응답을 기다리지 않는다.
- `onAllSettled` 를 적지 않으면 `optimistic` 은 언제나 `inflight` 의 일부다.
- **겹은 `optimistic` 으로 얹는다.** README 의 `select` 예시를 `inflight` 에서 `optimistic` 으로 고친다. 0.5 설계 §3 「쓰는
  모습」의 예시는 본문을 두고 이 문서를 가리키는 한 줄만 단다(§6). `select` 가 `optimistic` 을 읽는 것도 0.5 설계 §2.2 대로
  따라간다.

### 2.3 `onAllSettled` — 모든 호출이 끝나면 한 번 확인한다

```ts
{
  onAllSettled?: { [name]?: () => unknown },
}
```

- **적지 않으면 돌지 않는다.** 기본은 확인하지 않는 것이다.
- 그 바꾸기의 `inflight` 가 빌 때마다 한 번 부른다. 호출이 하나뿐이었어도, 마지막 호출이 실패했어도 부른다. 응답은 실패로
  왔지만 서버는 값을 바꾼 뒤 연결이 끊겼을 수 있기 때문이다.
- **무엇을 다시 받을지는 쓰는 사람이 적는다.** 바꾸기만 가진 자원은 그 대상을 모른다. 한 key 에 있으면 `ctx().invalidate()`,
  다른 key 에 있으면 `ctx('api.workspace.getSettings').invalidate()` 처럼 적는다.
- 돌려준 값이 Promise 면 그것이 끝날 때까지 기다린다. 이 동안을 **확인 중**이라 한다.

**확인 중에는 겹을 남긴다.** `onAllSettled` 를 적었으면 끝난 호출(성공이든 실패든, 밀려나지 않은 것)이 `optimistic` 에서 빠지지
않고 확인을 기다린다. 확인이 끝나고 그때 `inflight` 도 비어 있으면 기다리던 호출을 모두 뺀다. 그래야 확인 응답이 오기 전에 옛
캐시가 한 번 그려지는 일이 없다. TanStack 이 `onSettled` 에서 `invalidateQueries` 의 Promise 를 돌려주게 하는 것과 같은 까닭이다.

- 확인을 기다리는 호출도 §2.1 대로 밀려난다. 나중 호출이 성공하면 그 앞의 것은 기다리지 않고 바로 빠진다.
- 확인 중에 새 호출이 들어오면 그 호출들이 모두 끝날 때 확인을 한 번 더 한다. 앞 확인이 끝나도 그때 `inflight` 가 비어 있지
  않으므로 기다리던 호출은 남는다.
- **확인 응답이 새 호출의 결과를 덮지 않는다.** 새 호출의 `onSuccess` 가 `setData` 하면 그 칸의 차례가 오르고, 그보다 먼저 떠난
  확인 응답은 칸에 적히지 않는다. 0.4 부터 있는 `setData` 의 동작(`src/query.ts` 의 `setOne`)이고 새로 짓지 않는다.
- **확인이 실패하면 확인이 끝난 것으로 본다.** 기다리던 호출은 빠지고 캐시는 마지막 `onSuccess` 가 남긴 값이다. 실패가 남는 자리는
  확인을 어떻게 적었는가에 따라 갈린다.
  - `invalidate()` 로 적었으면 실패는 다시 받은 칸의 `error` 에 남는다. `invalidate` 는 받기가 실패해도 거부되지 않는다.
  - 쓰는 사람의 함수가 직접 던지거나 거부되는 Promise 를 돌려주면 콘솔에 남긴다.
- `pending` 은 확인 중에 `false` 다. 요청이 오가는 중인지를 말하는 칸이기 때문이다. 확인 중인지를 따로 드러내지 않는다.
- 각 호출의 `mutateAsync` 는 확인을 기다리지 않고 자기 결과로 끝난다.

### 2.4 호출 하나의 차례 — 0.5 설계 §2.4 를 바꾼다

1. 호출 번호와 인자를 `inflight` · `optimistic` 에 넣고, `error` 를 지우고, 알린다. `scope` 가 있으면 줄 차례를 기다린다.
2. 바꾸기 함수를 부른다.
3. 밀려났는지 견준다.
4. 밀려나지 않았으면 `data` 또는 `error` 를 적고 `onSuccess` 또는 `onError`, 그다음 `onSettled` 를 부른다. 성공이면 앞 호출들을
   밀어낸다(`optimistic` 에서 뺀다).
5. **그 뒤에** 그 호출을 `inflight` 에서 뺀다. `onAllSettled` 가 없으면 `optimistic` 에서도 뺀다. 알린다.
6. `inflight` 가 비었고 `onAllSettled` 가 있으면 확인을 부르고 기다린 뒤, 그때도 `inflight` 가 비었으면 기다리던 호출을
   `optimistic` 에서 빼고 알린다.

### 2.5 이미 구현했지만 0.5 설계에 적지 않은 판정

0.5 를 짓는 동안 정한 것을 여기에 적는다. 동작은 바꾸지 않는다.

- **호출을 시작하면 `error` 를 지운다.** 다시 누르면 앞 실패의 문구가 사라진다. 0.2 의 화면별 바꾸기와 같다.
- **실패해도 앞의 `data` 는 남는다.** `data` 는 마지막 성공의 결과다.
- **`reset()` 은 칸만 막고 콜백은 막지 않는다.** `reset` 앞에 보낸 호출의 결과는 `data` · `error` 에 적지 않지만 `onSuccess`
  들은 돈다. 캐시를 서버 값으로 맞추는 일이 `onSuccess` 에 있기 때문이다. `optimistic` 도 `reset` 과 상관없이 §2.2 대로 움직인다.

## 3. 쓰는 모습

```ts
createStore('api.workspace.appearance', (_set, _get, ctx) =>
  createResource(() => ({
    query: fetchAppearance,
    async patch(p: AppearancePatch) { return readAppearance(await http.patch('/api/appearance', p)) },
  }), {
    onSuccess: { patch: (next) => ctx().setData(next) },
    onAllSettled: { patch: () => ctx().invalidate() },
    select: (s) => ctx().patch.optimistic.reduce((acc, [p]) => acc.with(p), s),
  }),
)
```

**서버가 차례를 지키지 않을 때.** 빨강을 먼저, 초록을 나중에 보냈다. 서버는 초록을 먼저 처리했고 응답도 초록이 먼저 왔다.
서버의 마지막 값은 빨강이다. 아래 표는 위 코드처럼 `onAllSettled` 를 적었을 때다.

| 때 | `inflight` | `optimistic` | 캐시 | 화면 |
|---|---|---|---|---|
| 빨강 · 초록을 보낸 직후 | `[빨강, 초록]` | `[빨강, 초록]` | 파랑 | 초록 |
| 초록이 성공했다 — 빨강이 밀려난다 | `[빨강]` | `[초록]` | 초록 | 초록 |
| 빨강이 성공했다 — 밀려났으므로 버린다 | `[]` | `[초록]` | 초록 | 초록 |
| `onAllSettled` 의 다시 받기가 끝났다 | `[]` | `[]` | 빨강 | 빨강 — 서버와 같다 |

`onAllSettled` 를 적지 않으면 둘째 줄에서 `optimistic` 이 빈다. 초록은 끝났으므로 확인을 기다리지 않고 빠지고, 빨강은 밀려나
빠진다. 넷째 줄은 없고 화면은 서버와 다른 초록으로 남는다.

**나중 호출이 실패할 때.** 빨강을 먼저, 초록을 나중에 보냈다. 초록이 먼저 실패했다. 아래 표는 `onAllSettled` 를 적지 않았을 때다.

| 때 | `inflight` | `optimistic` | 캐시 | `error` | 화면 |
|---|---|---|---|---|---|
| 초록이 실패했다 — 아무것도 밀어내지 않는다 | `[빨강]` | `[빨강]` | 파랑 | 초록의 문구 | 빨강 |
| 빨강이 성공했다 | `[]` | `[]` | 빨강 | `null` | 빨강 |

0.5 는 둘째 줄에서 빨강의 응답을 늦은 것으로 버려 캐시가 파랑으로 남았다.

위 코드처럼 `onAllSettled` 를 적었으면 실패한 초록도 확인이 끝날 때까지 겹에 남는다(§8 의 1).

| 때 | `inflight` | `optimistic` | 캐시 | `error` | 화면 |
|---|---|---|---|---|---|
| 초록이 실패했다 | `[빨강]` | `[빨강, 초록]` | 파랑 | 초록의 문구 | 초록 |
| 빨강이 성공했다 — 빨강은 확인을 기다리고 초록은 밀려나지 않는다 | `[]` | `[빨강, 초록]` | 빨강 | `null` | 초록 |
| 확인의 다시 받기가 끝났다 | `[]` | `[]` | 빨강 | `null` | 빨강 |

둘째 줄에서 실패 문구는 사라졌는데 화면은 서버가 거부한 초록을 보인다. 확인이 끝나야 서버 값이 된다.

## 4. 고려한 길

- **밀려난 호출을 `inflight` · `pending` 에서 뺀다.** 겹은 바로 고쳐지지만 두 칸이 「아직 오가는 요청」이라는 뜻을 잃는다. 겹 전용
  칸 `optimistic` 을 따로 두었다.
- **`onAllSettled` 대신 `true` 로 켜기만 한다.** 받기와 바꾸기가 다른 key 에 있으면 바꾸기만 가진 자원이 다시 받을 대상을 모른다.
  0.5 설계 §4 「고려한 길」이 이 까닭으로 「겹친 호출이 모두 끝난 뒤 다시 받아 덮는다」를 버렸는데, 대상을 쓰는 사람이 적게 하면
  그 까닭이 사라진다.
- **두 호출 이상이 겹친 적이 있을 때만 확인한다.** 순서 문제는 겹칠 때만 생기므로 요청을 아낀다. 하지만 서버가 다른 경로로 값을
  바꾸는 경우와 실패 뒤 서버 값이 바뀐 경우를 덮지 못한다. `inflight` 가 빌 때마다 확인한다(사람이 정했다).
- **이름.** `succeeded` 는 성공했을 때만 도는 것으로 읽힌다. 이 콜백은 실패 뒤에도 돈다. 라이브러리의 `onSettled` 와 JS 표준의
  `Promise.allSettled` 를 이은 `onAllSettled` 로 정했다(사람이 정했다).

## 5. 깨지는 것과 버전

- 나중 호출이 실패하면 앞 호출의 응답이 더는 버려지지 않는다. 그 `onSuccess` 가 돈다.
- `select` 가 `inflight` 로 겹을 얹던 코드는 그대로 돌지만 밀려난 호출이 남는 결함도 그대로다. `optimistic` 으로 옮겨야 한다.

0.5.0 은 npm 에 나가지 않았다(`pnpm test:pack` 의 기존 실패가 `prepublishOnly` 를 막는다). 그래서 **버전은 0.5.0 그대로 두고
이 보완을 0.5 에 담는다.** README 의 설치 줄 `"supa-store": "^0.4.0"` 을 `^0.5.0` 으로 고친다.

## 6. 함께 고칠 자리

- `src/index.ts` 의 `Ctx` 주석 「구독은 없다」를 `select` 안에서 바꾸기 상태를 읽으면 따라간다는 것으로 고친다.
- README: 겹 예시를 `optimistic` 으로 고치고, `onAllSettled` 와 「서버가 차례를 지키지 않으면」을 함정 절에 적는다. TanStack 과
  다른 점에 「콜백은 밀려난 응답에서 부르지 않는다」를 「늦은 응답」 대신 적는다.
- 0.5 설계 §2.4 의 「늦은 응답」 문단과 §8 「시험」의 해당 줄 머리에 이 문서를 가리키는 한 줄을 단다. 본문은 고치지 않는다.

## 7. 시험

- 나중 호출이 성공하면 앞 호출이 그 순간 `optimistic` 에서 빠지고 `inflight` 에는 응답 때까지 남는다.
- 밀려난 호출의 응답은 `data` · `error` 를 고치지 않고 콜백을 부르지 않으며, 그 `mutateAsync` 는 자기 결과로 끝난다.
- 나중 호출이 먼저 실패해도 앞 호출의 성공은 `data` 를 적고 `onSuccess` 를 부른다(§3 둘째 표).
- `onAllSettled` 를 적지 않으면 아무것도 다시 받지 않고, 마지막 호출이 끝나면 `optimistic` 이 빈다.
- `onAllSettled` 를 적으면 `inflight` 가 빌 때마다 정확히 한 번 부른다. 호출 하나 · 마지막 호출 실패에서도 부른다.
- 확인의 Promise 가 끝나기 전에는 `optimistic` 이 남고, 끝난 뒤 빈다. 그 사이 `pending` 은 `false` 다.
- 확인 중에 새 호출이 들어오면 앞 확인이 끝나도 `optimistic` 이 비지 않고, 새 호출이 모두 끝난 뒤 확인을 한 번 더 부른다.
- 확인 중에 새 호출이 성공해 `setData` 하면, 그보다 먼저 떠난 확인 응답은 캐시를 덮지 않는다.
- `invalidate()` 의 다시 받기가 실패하면 `optimistic` 이 비고 그 실패는 받은 칸의 `error` 에 남는다.
- 함수가 직접 던지거나 거부되는 Promise 를 돌려줘도 `optimistic` 이 비고 콘솔에 남는다.
- §3 첫째 표를 그대로 재현한다 — 서버가 차례를 지키지 않아도 마지막 화면이 서버 값이다.
- `scope` 와 함께 적어도 차례대로 나가고 마지막에 한 번 확인한다.
- **타입 시험:** `optimistic` 의 원소가 바꾸기 함수의 `Parameters` 다. 없는 바꾸기 이름을 `onAllSettled` 의 열쇠로 적으면 타입 오류다.

## 8. Claude 가 정한 것 — 사람이 확인할 것

1. **실패한 호출도 확인을 기다리는 동안 겹에 남는다(§2.3).** 실패가 서버에 적혔을 수도 있으므로, 겹을 뺐다가 확인 응답으로 다시
   그리는 깜박임을 피했다. 확인을 켜지 않았으면 0.5 처럼 실패하자마자 빠진다.
2. **확인 중임을 드러내는 칸을 두지 않는다(§2.3).** 쓰임새가 생기면 더한다.
3. **버전을 0.5.0 그대로 둔다(§5).** 0.5.0 이 나간 적이 없기 때문이다.
4. **`error` · `data` 는 마지막으로 끝난, 밀려나지 않은 호출을 따른다(§2.1).** 그래서 나중 호출의 실패 문구가 앞 호출의 성공으로
   지워질 수 있다. 서버의 값과 맞는 쪽을 골랐다.

## 9. 빌더에게 맡기는 것

- 밀려남을 판정하는 자료(가장 큰 성공 번호 하나면 된다)와 `reset` 의 `floor` 를 함께 두는 방법.
- 확인을 기다리는 호출을 `optimistic` 에 남겨 두는 자료 구조.
