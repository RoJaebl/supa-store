# supa-store 0.3 — 서버와 실시간으로 이어진 연결을 store 로 꺼낸다

- 날짜: 2026-10-25 시작, 2026-10-26 정식 설계로 다시 썼다
- 상태: 사람의 승인 전
- 앞선 설계: 같은 폴더 `2026-10-25-supa-store-0.2-design.md` — 그 문서의 §13 「바깥 엔진은 0.3 이 맡는다」를 이 문서가 받는다.
  0.2 의 `MutationView`(`mutate` · `mutateAsync`), `status` · `isFetching` 규칙(§16 19번)을 그대로 쓴다

## 1. 의도

editor 에는 React 밖에서 스스로 바뀌는 엔진이 셋 있다. 문서 협업 소켓, 터미널 세션, 언어 서버 연결이다. 0.2 까지는 store 의
creator 안에서 엔진을 만들고 `subscribe` 해 `set` 하는 꼴로 감싼다. 그 꼴에는 닫기의 자리가 없어, 개발 모드의 다시 등록과 시험의
`overrideStore` · `resetStores` 로 store 를 다시 지을 때 앞 연결이 열린 채 남는다. 그리고 끊겼다 다시 잇기, 놓친 바뀜 따라잡기,
명령의 답 받기를 엔진마다 손으로 짓는다.

이 판은 그런 연결을 `createResource` 처럼 도우미 하나로 정의하게 한다. 라이브러리를 만드는 쪽에서 설계하므로 **연결의 약속까지
supa-store 가 정하고, 서버는 그 약속에 맞춰 짓는다.** 서버 쪽은 그 약속을 지키는 도우미(「한 홉」)를 함께 내서, 앱이 짓는 것을
「바뀌면 `publish`」와 「지금 값 전체를 주는 `snapshot`」 둘로 줄인다. 그리고 언어 서버처럼 우리 약속을 모르는 상대를 위해
JSON-RPC 2.0 을 그대로 말하는 도우미를 하나 더 둔다.

## 2. 목표

1. `createStore(key, () => createStream({ url, … }))` 로 웹소켓 또는 SSE 연결 하나를 store 로 정의하고, 화면은 `useStore` 로
   `data` · `status` · `isFetching` · `error` 와 명령(`mutate` · `mutateAsync`)을 꺼낸다.
2. 연결은 처음 꺼낼 때 열리고, store 를 다시 지을 때 닫힌다. 다시 지어도 앞 연결 · 타이머 · 리스너가 남지 않는다.
3. 끊기면 스스로 다시 잇고, 끊긴 동안의 바뀜을 따라잡는다. 다시 잇는 동안 마지막 값을 그대로 보인다.
4. 보낸 뒤 끊긴 명령은 다시 이으면 결과를 확인한다. 같은 명령이 두 번 실행되지 않는다.
5. 서버는 `createStreamServer` 하나로 약속을 지킨다. Node `http` 서버와 Web 표준 처리기 양쪽에 붙는다.
6. `createJsonRpc` 로 JSON-RPC 2.0 상대(언어 서버 프로세스의 표준 입출력, 웹소켓)에 붙어 같은 꼴로 store 에 꺼낸다. 서버(Node)와
   브라우저 양쪽에서 돈다.
7. 0.2 의 정의 파일과 화면 코드는 고치지 않고 돈다.

## 3. 하지 않는 것

- **프로세스 띄우기 · 끝내기.** pty, 언어 서버 프로세스의 일생은 서버 앱이 쥔다. supa-store 는 앱이 연 연결 · 스트림만 받는다.
- **도메인 로직.** 터미널 출력 합치기, 문서 편집 합치기, 언어 서버 메시지의 뜻은 앱이 정한다. 바뀜의 꼴도 앱이 정한다(JSON Patch
  같은 꼴을 라이브러리가 정하지 않는다).
- **인증 판단.** 홉은 판단을 부를 자리와 신원을 실어 나를 길만 준다.
- **Web 표준 처리기에서의 웹소켓.** 런타임마다 갈아타는 방법이 달라 이 판에서는 SSE 만 받는다(§9.3).
- **개발 중 앞 연결을 이어 가기.** 엔진을 감싼 정의 파일을 고치면 그 연결은 다시 열린다(사람이 받아들였다).
- **여러 서버 사이의 기록 나누기.** 홉의 짧은 기록은 그 서버 프로세스의 메모리에만 있다. 서버가 여러 대이거나 다시 뜨면
  `snapshot` 으로 되돌아간다.
- **store 를 서버용으로 빌드하는 기능.** 나중에 고려한다(§16).

## 4. 실패로 보는 것

- store 를 다시 지은 뒤 앞 연결 · heartbeat 타이머 · 다시 잇기 타이머 · 리스너가 남는다.
- 잠깐 끊겼다 이어질 때 화면의 값이 비었다 돌아온다.
- 끊긴 동안의 바뀜이 빠지거나 두 번 덧붙는다.
- 보낸 뒤 끊긴 명령이 다시 보내져 두 번 실행된다.
- 명령의 `pending` 이 영영 풀리지 않는다.
- 토큰이 주소의 쿼리에 실려 서버 · 프록시 기록에 남는다.
- 서버 앱이 버전 · 기록 · 답 기록을 손으로 지어야 약속을 지킬 수 있다.

## 5. 고려한 길

| 물음 | 고른 길 | 버린 길과 까닭 |
|---|---|---|
| 바깥 자원의 생명주기 | 처음 꺼낼 때 열고, 다시 지을 때만 닫는다. 개발 · 제품의 코드를 가르지 않는다 | 보는 쪽이 없으면 닫는 꼴(Jotai `onMount` · Nanostores · RTK Query): 탭을 닫으면 터미널이 끊겨 다시 열 때마다 이어 붙여야 한다 |
| 무엇이라 부르나 | `createStream` — 브라우저가 쥐는 것은 서버와 이어진 연결이다 | `createProcess`: 프로세스는 서버에서 돈다. 라이브러리가 프로세스를 띄우는 것처럼 읽힌다 |
| 연결의 약속을 누가 정하나 | supa-store 가 정하고 서버가 맞춘다 | 쓰는 쪽이 서버와 약속을 맺는 꼴: 다시 잇기 · 따라잡기를 엔진마다 짓는다 |
| 서버 쪽 상태를 누가 쥐나 | 홉이 버전 · 짧은 기록 · 답 기록을 쥐고, 앱은 `publish` · `snapshot` 만 짓는다 | 홉이 값 전체를 쥐는 꼴: 서버 여러 대 · 재시작을 홉이 못 다룬다. 앱이 버전 · 기록을 쥐는 꼴: 약속을 지키는 일이 앱마다 남는다 |
| `publish` 가 무엇을 보내나 | 바뀐 부분. 클라이언트가 `reduce` 로 합친다 | 값 전체만: 터미널 출력처럼 자라는 값에서 기록이 금방 MB 단위가 된다 |
| 명령에 답이 오나 | 온다. 0.2 의 바꾸기와 같은 꼴로 꺼낸다 | 보내기만: 세션 id · 완성 목록 같은 결과를 바뀜에서 짐작해야 한다 |
| 끊긴 동안 부른 명령 | 곧바로 실패한다 | 쥐었다 다시 보내기: 두 번 실행될 수 있고 중복 거르기가 앱의 일이 된다 |
| 서버 도우미가 붙는 자리 | Node `http` 와 Web 표준 처리기 둘 다 | 하나만: 쓰는 틀이 갈린다 |
| 우리 약속을 모르는 상대 | JSON-RPC 2.0 을 그대로 말하는 도우미를 따로 둔다 | 서버 앱이 바꿔 내놓기만: 서버가 서버와 말하는 경우와 이미 JSON-RPC 를 말하는 상대를 다루지 못한다 |

견준 것: Centrifugo, Socket.IO 4.6 의 연결 상태 복구, tRPC v11 구독(`tracked`), Phoenix Channels, graphql-ws · graphql-sse,
SSE 의 `Last-Event-ID`, HTTP `Idempotency-Key`, MQTT QoS 2, Zustand · Pinia · Jotai · Nanostores · RTK Query 의 생명주기.

## 6. 생명주기

- **처음 꺼낼 때 연다.** store 가 처음 지어질 때 도우미가 연결을 연다(0.1.0 의 「처음 꺼낼 때 짓는다」 그대로).
- **다시 지을 때만 닫는다.** 개발 모드의 다시 등록, `overrideStore`, `resetStores` 다. 보는 화면이 없어져도 닫지 않는다.
- 제품 빌드에서는 store 를 다시 짓지 않으므로 닫기가 일어나지 않는다. 같은 코드가 제품에서는 「앱 내내 산다」, 개발에서는 「그
  정의 파일을 고칠 때 다시 연다」로 동작한다.
- **닫기 표식.** `createStream` · `createJsonRpc` 가 돌려주는 상태에 `[USE]` 와 같은 꼴의 심볼 표식(`[DISPOSE]`)을 둔다.
  `src/index.ts` 의 `build` 가 다시 짓기 직전에 앞 상태의 `[DISPOSE]` 를 부른다. 0.2 의 자원에는 이 표식이 없으므로 동작이
  바뀌지 않는다.
- **`createStream` 은 `typeof window === "undefined"` 이면 연결을 열지 않는다**(서버에서 그릴 때). 이때 상태는 `loading` 그대로다.
  시험처럼 Node 에서 열어야 하면 `createStream({ open: "always" })` 로 연다.
- **`createJsonRpc` 는 환경을 가리지 않고 지어질 때 연다.** 서버에서도 쓰는 도우미이기 때문이다. 정의 파일이 서버에서 평가되더라도
  store 는 처음 꺼낼 때 지어지므로, 꺼내지 않으면 열리지 않는다. store 없이 바로 쓸 때는 `createJsonRpc(...)` 를 부르는 순간 연다.
- **`disposeStores()` 를 더한다.** 다시 짓지 않고 모든 store 의 `[DISPOSE]` 를 부른 뒤 지어지지 않은 상태로 되돌린다. 시험이 끝날 때
  열린 연결 · 타이머를 닫는 자리다. `resetStores()` 는 지금처럼 다시 짓는다(그래서 연결을 닫았다 곧바로 연다).
- 다시 지을 때 그 store 를 짓는 동안 `ctx` 로 꺼낸 store 도 함께 다시 지어지는 것은 0.1.0 그대로다.

## 7. 연결의 약속

### 7.1 메시지

메시지는 JSON 객체 하나이고 `t` 칸이 갈래를 가른다.

| 방향 | `t` | 담는 것 | 언제 |
|---|---|---|---|
| 서버 → 클라이언트 | `welcome` | `epoch`, `version`, `connection` | `hello` 를 받아 인증을 통과한 직후. 따라잡을 것이 없어도 늘 보낸다 |
| 서버 → 클라이언트 | `snapshot` | `version`, `value` | 처음 붙을 때, 버전이 기록 밖일 때, `epoch` 가 바뀌었을 때 |
| 서버 → 클라이언트 | `change` | `version`, `change` | 앱이 `publish` 할 때 |
| 서버 → 클라이언트 | `reply` | `id`, `ok`, `result` 또는 `error`, `version` | 명령에 답할 때. `version` 은 답할 때의 채널 버전 |
| 서버 → 클라이언트 | `fate` | `id`, `state`(`done` · `unknown-id` · `running`), `done` 이면 `reply` 와 같은 칸 | 클라이언트가 끊긴 명령의 결과를 물을 때 |
| 서버 → 클라이언트 | `request` | `id`, `method`, `params` | 서버가 클라이언트에 물을 때(§7.6) |
| 서버 → 클라이언트 | `ping` | — | heartbeat |
| 서버 → 클라이언트 | `close` | `code`, `reason` | 서버가 일부러 닫을 때(SSE 에서; 웹소켓은 닫기 코드로) |
| 클라이언트 → 서버 | `hello` | `version`(가진 것이 있으면), `channel`, `auth`(웹소켓일 때) | 연결 직후 첫 메시지 |
| 클라이언트 → 서버 | `command` | `id`, `name`, `args` | 명령을 부를 때 |
| 클라이언트 → 서버 | `ask` | `ids` | 다시 이은 뒤 끊긴 명령의 결과를 물을 때 |
| 클라이언트 → 서버 | `answer` | `id`, `ok`, `result` 또는 `error` | 서버의 `request` 에 답할 때 |
| 클라이언트 → 서버 | `pong` | — | `ping` 에 답할 때 |

### 7.2 버전과 짧은 기록

- **버전은 홉이 매긴다.** 채널(§9.1)마다 0 에서 시작해 `publish` 할 때마다 1씩 올린다. 앱은 버전을 몰라도 된다.
- **홉은 채널마다 최근 바뀜을 쥔다.** 기본은 최근 1000 개 또는 최근 5분 가운데 짧은 쪽이다. `createStreamServer({ history })` 로
  바꾼다.
- **`epoch`** 는 홉이 뜰 때마다 새로 정하는 무작위 글자다. 서버가 다시 뜨면 버전이 0 부터 다시 세므로, 클라이언트는 `hello` 에 가진
  `epoch` 를 함께 보내고, 홉은 `epoch` 가 다르면 버전을 보지 않고 `snapshot` 을 보낸다.
- 클라이언트의 `hello.version` 이 같은 `epoch` 의 기록 안이면 그 뒤의 `change` 를 차례로 보낸다. 기록 밖이거나 없으면 앱의
  `snapshot(ctx)` 을 불러 `snapshot` 을 보내고, 그 버전부터 이어 간다. 따라잡기는 `welcome` 뒤에 오는 것까지이며, 클라이언트는
  `welcome.version` 에 이르면 `isFetching` 을 끈다.
- **`snapshot(ctx)` 은 동기 함수다.** 홉은 그것을 부르는 순간의 버전을 그 값의 버전으로 친다. 비동기로 받으면 기다리는 동안의
  `publish` 가 값에 들었는지 홉이 알 수 없어, 바뀜이 빠지거나 두 번 붙는다. 값을 비동기로 모아야 하는 앱은 미리 메모리에 쥐어 둔다.
- 앱이 버전을 직접 붙이는 길(DB 의 순번 등)은 이 판에서 두지 않는다(§16). 순번은 중간이 비기 쉬워 §7.3 의 건너뛰기 판정과 맞지 않는다.

### 7.3 바뀜과 `reduce`

- 바뀜의 꼴은 쓰는 쪽이 정한다. 터미널이면 `{ op: "append", id, chunk }` 처럼 도메인에 알맞은 꼴이다.
- 클라이언트는 `reduce(value, change) => value` 로 합친다. `snapshot` 을 받으면 그 값에서 시작하고, 뒤의 `change` 를 차례로 합친다.
- `reduce` 를 주지 않으면 바뀜을 새 값 전체로 본다.
- 클라이언트는 가진 버전보다 작거나 같은 `change` 를 버린다(늦게 온 앞 연결의 메시지). 버전이 하나 넘게 건너뛰면 그 연결을 닫고
  다시 이어 `hello` 로 따라잡는다.

### 7.4 명령과 답, 답 기록

- 명령마다 클라이언트가 요청 id(무작위 글자)를 붙인다. 서버는 같은 id 로 `reply` 한다.
- **명령은 그 명령이 낸 바뀜이 `data` 에 든 뒤에 끝난다.** `reply.version` 은 답할 때의 채널 버전이고, 클라이언트는 `data` 가 그 버전에
  이른 뒤에 `mutateAsync` 를 끝낸다. 그래서 `await open.mutateAsync()` 바로 뒤의 `data` 에 새 세션이 든다. SSE 처럼 답과 바뀜이 다른
  길로 오는 전송에서 특히 필요하다.
- **답의 제한 시간은 기본 30초다.** `createStream({ timeout })` 으로 연결마다, `commands: { 이름: { timeout } }` 으로 명령마다 바꾼다.
  지나면 그 명령은 「응답 지연」으로 실패하고 뒤늦게 온 답은 버린다.
- **끊긴 동안 부른 명령은 곧바로 「연결 끊김. 명령 실패」로 실패한다.** 쥐었다 다시 보내지 않는다.
- **홉은 채널마다 최근 명령의 요청 id 와 답을 쥔다.** 쥐는 기간은 §7.2 의 기록과 같은 규칙이다.
- 보낸 뒤 답을 받기 전에 끊긴 명령은 `pending` 으로 남는다. 다시 이으면 클라이언트가 `ask` 로 묻는다.
  - `done`: 그 답으로 끝낸다(성공 또는 실패).
  - `unknown-id`: 「연결 끊김. 명령 실패」로 끝낸다. 다시 보내도 안전하다.
  - `running`: 답을 기다린다(제한 시간은 다시 센다).
  - 다시 잇지 못하거나 서버가 기록을 잃었으면(서버가 다시 떴다는 것을 `hello` 의 답으로 안다): 「연결 끊김. 알 수 없음」으로 끝낸다.
- 같은 요청 id 로 다시 보내면 홉은 처리하지 않고 쥔 답을 돌려준다. 그래서 「다시 보내기」 버튼은 같은 id 로 보낸다.
- SSE 에서는 명령을 HTTP `POST` 로 보내고 그 응답이 `reply` 다. `ask` · `answer` 도 `POST` 다. 이 `POST` 들은 `welcome.connection` 을
  `X-Supa-Connection` 헤더에 실어 어느 스트림 연결의 것인지 밝힌다. 서버는 `POST` 마다 `authorize` 를 다시 부르고, 신원과 채널이 그
  연결의 것과 같은지 본다.

### 7.5 heartbeat 와 다시 잇기

- 서버가 25초마다 `ping` 을 보낸다. 클라이언트는 `pong` 으로 답한다(SSE 는 `ping` 만 받고 답하지 않는다).
- 클라이언트가 60초 동안 아무 메시지도 받지 못하면 끊긴 것으로 보고 다시 잇는다.
- 다시 잇기 간격은 1초에서 시작해 두 배씩 늘리고 30초에서 멈춘다. 매번 ±20% 를 흔들어(jitter) 한꺼번에 몰리지 않게 한다.
  이어지면 1초로 되돌린다.
- 창이 가려져도 다시 잇는다(0.2 의 주기 받기와 다르다 — 연결은 알림을 받는 길이라 멈추면 따라잡을 것이 쌓인다).

### 7.6 서버가 클라이언트에 묻는 요청

- 서버가 `request` 를 보내면 클라이언트는 `createStream({ handlers })` 의 같은 이름 함수를 불러 `answer` 로 돌려준다.
- 홉이 `ctx.request(method, params)` 로 이것을 부르고, 답을 Promise 로 받는다. 제한 시간과 끊김 규칙은 §7.4 와 같다(방향만 반대).
- 핸들러가 없는 이름이면 클라이언트가 `ok: false` 로 답한다.

### 7.7 닫기 신호

- **웹소켓:** supa-store 는 닫기 코드 4000~4099 를 쓴다. 4001 은 「다시 오지 마라」(인증 거절 · 서버가 일부러 닫음)이고, 클라이언트는
  다시 잇지 않는다. 4000 은 「곧 다시 와라」(서버가 내려가는 중)이고, 클라이언트는 곧바로 다시 잇는다. 그 밖의 닫힘은 모두 다시
  잇는다.
- **SSE:** 서버가 `close` 메시지에 `code` · `reason` 을 실어 보내고 응답을 끝낸다. 연결을 열 때 HTTP 401 · 403 이 오면 4001 과 같이
  읽는다.

## 8. 클라이언트 — `createStream`

### 8.1 정의

```ts
// src/infra/terminal/terminal.state.ts
import { createStore } from "supa-store";
import { createStream } from "supa-store/stream";

type Change = { op: "open"; session: TerminalSession } | { op: "append"; id: string; chunk: string } | { op: "exit"; id: string };

createStore("infra.terminal", () =>
  createStream<TerminalSession[], Change>({
    url: "/ws/terminal",
    transport: "ws",                       // 또는 "sse"
    channel: "default",                    // 생략하면 "default"
    auth: () => getToken(),                // 생략하면 쿠키만
    reduce: (sessions, c) =>
      c.op === "open" ? [...sessions, c.session]
      : c.op === "append" ? sessions.map((s) => (s.id === c.id ? { ...s, output: s.output + c.chunk } : s))
      : sessions.map((s) => (s.id === c.id ? { ...s, alive: false } : s)),
    commands: {
      open: (cwd: string) => ({}) as string,   // 이름과 인자 · 결과 타입만 적는다 — 몸은 쓰이지 않는다
      write: (id: string, text: string) => ({}) as void,
      kill: { timeout: 5_000 } as unknown as (id: string) => void,
    },
    handlers: {
      // 서버가 묻는 요청에 답한다
      confirm: async (message: string) => window.confirm(message),
    },
    timeout: 30_000,
  }),
);
```

명령을 타입으로 적는 꼴(`commands` 의 값)은 §15 가 빌더에게 맡긴다. 위 꼴은 뜻을 보이려는 초안이다.

### 8.2 화면이 꺼내는 칸

```tsx
const { data, status, isFetching, error, open } = useStore("infra.terminal", {
  pick: ["data", "status", "isFetching", "error", "open"],
});
const id = await open.mutateAsync("/repo");
```

- `data` · `status` · `isFetching` · `error`: 연결과 값. 0.2 의 `QueryView` 와 같은 이름과 규칙이다.
- 명령마다 0.2 의 `MutationView`(`mutate` · `mutateAsync` · `pending` · `error` · `data` · `reset`).
- `pick` · `omit` 은 0.2 와 같고, 고른 칸이 바뀔 때만 다시 그린다.
- store 끼리는 `ctx("infra.terminal").open("/repo")` 로 명령을 바로 부른다. 실패는 던진다(0.2 의 바꾸기와 같다).

### 8.3 연결 상태

| 때 | `data` | `status` | `isFetching` | `error` |
|---|---|---|---|---|
| 처음 연결 중 | `undefined` | `loading` | `true` | `null` |
| 이어져 값을 받는 중 | 지금 값 | `ready` | `false` | `null` |
| 끊겨 다시 잇는 중 | 마지막 값 그대로 | `ready` | `true` | 연결 끊김. 재시도 중.. |
| 다시 이어져 빠진 바뀜을 받았다 | 따라잡은 값 | `ready` | `false` | `null` |
| 서버가 「다시 오지 마라」로 닫았다 | 마지막 값 그대로 | `error` | `false` | 닫은 까닭 |
| 처음 연결이 「다시 오지 마라」로 거절됐다 | `undefined` | `error` | `false` | 닫은 까닭 |

마지막 값은 비우지 않는다. 연결 상태를 따로 담는 칸은 두지 않는다.

### 8.4 문구

| 자리 | 언제 보이나 | 문구 |
|---|---|---|
| 연결의 `error` | 연결이 끊겨 다시 잇는 동안 | 연결 끊김. 재시도 중.. |
| 명령의 `error` · `mutateAsync` 의 거절 | 끊긴 동안 부른 명령, 다시 이은 뒤 홉이 받은 적 없다고 답한 명령 | 연결 끊김. 명령 실패 |
| 같은 자리 | 보낸 뒤 끊겼고 다시 이은 뒤에도 결과를 확인하지 못한 명령 | 연결 끊김. 알 수 없음 |
| 같은 자리 | 제한 시간 안에 답이 오지 않은 명령 | 응답 지연 |

「재시도 중」은 연결에만 쓴다. 명령은 다시 보내지 않기 때문이다. 명령의 실패는 원래 오류 객체로 던지고, 그 `message` 가 위 문구다.
서버 앱이 `ok: false` 로 답한 실패는 앱이 보낸 문구를 그대로 쓴다.

### 8.5 SSE 의 받기

- 브라우저의 `EventSource` 는 헤더를 붙일 수 없으므로, SSE 는 `fetch` 의 응답 스트림을 읽어 받는다. `Authorization` 헤더에 `auth()`
  를 싣고, 다시 이을 때 `Last-Event-ID` 헤더에 가진 버전을 싣는다.
- 서버 → 클라이언트 메시지는 SSE 의 `data:` 한 줄 JSON 으로 오고, `snapshot` · `change` 에는 `id:` 로 버전이 붙는다.

## 9. 서버 — `createStreamServer` 와 두 진입점

### 9.1 정의

```ts
// server/terminal.stream.ts
import { createStreamServer } from "supa-store/server";

export const terminal = createStreamServer<TerminalSession[], Change>({
  authorize: async (ctx) => (await verify(ctx.token)) ?? ctx.reject("인증 실패"),   // 신원을 돌려주거나 거절한다
  channel: (ctx) => ctx.channel,                     // 클라이언트의 hello.channel — 기본은 그대로
  snapshot: (ctx) => sessionsOf(ctx.identity, ctx.channel),
  commands: {
    open: async (ctx, cwd: string) => {
      const id = spawnPty(cwd, (chunk) => terminal.publish(ctx.channel, { op: "append", id, chunk }));
      terminal.publish(ctx.channel, { op: "open", session: { id, cwd, output: "", alive: true } });
      return id;
    },
    write: (ctx, id: string, text: string) => writePty(id, text),
    kill: (ctx, id: string) => killPty(id),
  },
  history: { count: 1000, ms: 5 * 60_000 },
});
```

- `publish(channel, change, options?)`: 그 채널에 붙은 클라이언트 모두에게 보낸다. 홉이 버전을 붙이고 기록에 넣는다.
- `ctx`: `identity`(authorize 의 결과), `channel`, `token`, `request(method, params)`(§7.6), `reject(reason)`.
- 채널은 같은 연결 주소 안에서 값을 나누는 이름이다. 버전 · 기록 · 답 기록은 채널마다 따로 쥔다. 사람마다 다른 값을 주려면
  `channel` 에 신원을 넣는다.

### 9.2 Node `http` 서버에 붙이기

```ts
import { attachStream } from "supa-store/server/node";
attachStream(httpServer, { path: "/ws/terminal", stream: terminal });   // 웹소켓과 SSE 를 같은 주소에서 받는다
```

Express · Fastify · Koa 처럼 밑에 Node `http` 서버를 둔 틀은 이것으로 붙는다. 웹소켓은 선택 peer `ws` 로 받는다.

### 9.3 Web 표준 처리기

```ts
import { streamHandler } from "supa-store/server/web";
export const GET = streamHandler(terminal);    // SSE
export const POST = streamHandler(terminal);   // 명령 · ask · answer
```

`(req: Request) => Promise<Response>` 꼴이라 Hono · Next 라우트 처리기 · Bun · Deno 에 건다. **SSE 만 받는다.** Web 표준에는
웹소켓으로 갈아타는 길이 없어 런타임마다 다르고(Bun `server.upgrade` · Deno `Deno.upgradeWebSocket` · Hono 의 런타임별 도우미 ·
Cloudflare `WebSocketPair`), Next 라우트 처리기는 받지 못한다. 같은 약속이라 이런 틀의 앱은 `transport: "sse"` 로 같은 기능을
쓴다. 런타임별 웹소켓 어댑터는 요청이 생기면 더한다.

### 9.4 약속 처리는 한 벌

버전 · 기록 · 답 기록 · heartbeat · 닫기는 전송과 떼어 한 벌(`src/server/core`)만 짓는다. 두 진입점은 그 위의 겉이다.

## 10. 인증

- 클라이언트의 `auth()` 값은 웹소켓이면 `hello.auth` 로, SSE 면 `Authorization` 헤더로 싣는다. 명령의 `POST` 에도 같은 헤더를 싣는다.
  `auth` 를 주지 않으면 쿠키만 쓴다.
- 다시 이을 때마다 `auth()` 를 다시 부른다.
- 서버의 `authorize(ctx)` 가 거절하면 「다시 오지 마라」로 닫는다(§7.7). 웹소켓은 `hello` 를 받기 전까지 다른 메시지를 처리하지 않고,
  10초 안에 `hello` 가 오지 않으면 닫는다.
- 토큰을 주소의 쿼리로 싣지 않는다.

## 11. 우리 약속을 모르는 상대 — `createJsonRpc`

### 11.1 무엇을 하나

JSON-RPC 2.0 을 그대로 말한다. 언어 서버처럼 이미 JSON-RPC 를 말하는 상대에 중간 서버 없이 붙는다. store 로 꺼내는 틀과 생명주기는
`createStream` 과 같고, 상대가 모르는 우리 약속(버전 · 짧은 기록 · 답 기록 · 채널)은 듣지 않는다.

### 11.2 도는 자리와 연결

| 자리 | 붙는 상대 | 전송 |
|---|---|---|
| 서버(Node) | 서버 앱이 띄운 프로세스 | 표준 입출력. LSP 의 `Content-Length` 머리 꼴로 나눈다 |
| 서버(Node) | 다른 서버 | 웹소켓(`ws`) |
| 브라우저 | JSON-RPC 를 말하는 서버 | 웹소켓 |

프로세스나 연결은 앱이 열어 넘긴다. supa-store 는 요청 · 답 짝 맞추기, 알림, 제한 시간, 닫기만 맡는다. 프로세스의 일생은 앱에 남는다.

```ts
import { createJsonRpc } from "supa-store/rpc";

createStore("infra.lsp", (set, get, ctx) =>
  createJsonRpc({
    connect: () => {                                   // 열 때와 다시 이을 때 부른다
      const child = ctx("infra.lspProcess").spawn();   // 앱이 프로세스를 띄운다
      return { kind: "stdio", input: child.stdout, output: child.stdin };   // 또는 { kind: "ws", url }
    },
    initial: { diagnostics: {} as Record<string, Diagnostic[]> },
    reduce: (value, n) =>
      n.method === "textDocument/publishDiagnostics"
        ? { diagnostics: { ...value.diagnostics, [n.params.uri]: n.params.diagnostics } }
        : value,
    requests: { complete: "textDocument/completion", definition: "textDocument/definition" },
    notifications: { didOpen: "textDocument/didOpen", didChange: "textDocument/didChange" },
    handlers: { "workspace/applyEdit": async (edit) => ({ applied: await applyEdit(edit) }) },
    onReconnect: async (last, rpc) => {
      for (const uri of openFiles()) await rpc.notify("textDocument/didOpen", { textDocument: docOf(uri) });
      return last;
    },
    timeout: 30_000,
  }),
);
```

### 11.3 값과 상태

- `data`: `initial` 에서 시작해 알림을 `reduce` 로 합친 값.
- `requests` 의 이름마다 `MutationView`. `notifications` 의 이름마다 답을 기다리지 않는 함수.
- 연결 상태는 §8.3 의 표와 같다. 다시 이어도 마지막 값으로 이어 간다. 상대와 다시 맞추는 일은 `onReconnect(last, rpc)` 에서 쓰는 쪽이
  한다. 주지 않으면 마지막 값을 그대로 이어 간다. 비우려면 `initial` 을 돌려준다.
- 보낸 뒤 끊긴 요청은 곧바로 「연결 끊김. 알 수 없음」으로 끝난다. 끊긴 동안 부른 요청은 「연결 끊김. 명령 실패」, 제한 시간이 지나면
  「응답 지연」이다.
- 표준 입출력 상대는 「다시 잇기」가 곧 `connect` 를 다시 부르는 것이다. 프로세스가 끝나 입력이 닫히면 끊긴 것으로 보고 §7.5 의
  간격으로 `connect` 를 다시 부른다. 다시 띄울지는 앱의 `connect` 가 정한다.

### 11.4 서버에서 쓸 때

`createJsonRpc` 는 React 없이도 돈다. 서버 코드는 `createStore` 없이 `createJsonRpc(...)` 의 돌려준 객체를 바로 쓴다(`rpc.request` ·
`rpc.notify` · `rpc.on(method, fn)` · `rpc.close()`). 서버 앱이 언어 서버의 진단을 받아 `createStreamServer` 로 브라우저에 `publish`
하는 꼴이 이 자리다.

## 12. 하위 경로와 의존

| 하위 경로 | 담는 것 | 도는 자리 | 의존 |
|---|---|---|---|
| `supa-store/stream` | `createStream` | 브라우저 | 없다 |
| `supa-store/rpc` | `createJsonRpc` | 브라우저 · Node | 없다(Node 의 웹소켓은 `ws`, 선택 peer) |
| `supa-store/server` | `createStreamServer` | Node · Web 표준 런타임 | 없다 |
| `supa-store/server/node` | `attachStream` | Node | `ws`(선택 peer) |
| `supa-store/server/web` | `streamHandler` | Web 표준 런타임 | 없다 |

화면 쪽 진입점(`.` · `/react` · `/query` · `/stream`)의 런타임 의존 0개는 그대로다. `ws` 는 선택 peer 로 두고, 시험에는 개발 의존으로
들인다.

## 13. 시험

- 같은 Node 프로세스 안에서 `createStreamServer` + `attachStream` 과 `createStream` 을 함께 띄워 실제 웹소켓 · SSE 로 시험한다
  (vitest, jsdom 이 아닌 node 환경. 브라우저 `fetch` 스트림은 Node 의 `fetch` 로 대신한다).
- `createJsonRpc` 는 가짜 JSON-RPC 상대를 표준 입출력 쌍(`PassThrough` 둘)으로 붙여 시험한다.
- 이름을 붙여 둘 시험:
  - 다시 지으면 앞 연결 · heartbeat · 다시 잇기 타이머가 모두 멈춘다.
  - 끊긴 동안의 바뀜을 기록 안이면 `change` 로, 밖이면 `snapshot` 으로 따라잡는다. 두 번 덧붙지 않는다.
  - 보낸 뒤 끊긴 명령이 `ask` 로 `done` · `unknown-id` · `running` 각각에 맞게 끝난다. 같은 id 로 다시 보내면 두 번 실행되지 않는다.
  - 끊긴 동안 부른 명령은 곧바로 「연결 끊김. 명령 실패」다. 제한 시간이 지나면 「응답 지연」이다.
  - 4001 로 닫히면 다시 잇지 않고, 4000 이면 곧바로 다시 잇는다. SSE 의 401 은 4001 과 같다.
  - 토큰이 주소에 실리지 않는다.
  - 다시 잇는 동안 `data` 가 남고 `status` 가 `ready`, `isFetching` 이 `true` 다.
  - `createJsonRpc` 의 `onReconnect` 가 돌려준 값으로 이어 가고, 상대가 묻는 요청에 `handlers` 가 답한다.

## 14. Claude 가 정한 것 — 사람이 확인할 것

1. **메시지 갈래와 이름(§7.1).** `t` 칸 하나로 가르는 꼴과 각 이름. 틀리면 약속의 글자만 바뀐다.
2. **기록의 기본 크기: 최근 1000 개 또는 5분 가운데 짧은 쪽.** 터미널 출력처럼 바뀜이 잦은 줄기도 5분 끊김을 따라잡게 하려는 값이다.
3. **heartbeat 25초, 받지 못하면 60초 뒤 끊긴 것으로 본다.** 흔한 프록시의 쉬는 연결 끊기(대개 60초)보다 짧게 했다.
4. **다시 잇기 간격: 1초에서 두 배씩, 30초에서 멈추고 ±20% 를 흔든다.** 0.2 의 주기 늦추기(기본의 8배까지)와 다르게 위 끝을 시간으로
   둔 것은, 연결은 기본 간격이 쓰는 쪽마다 다르지 않기 때문이다.
5. **창이 가려져도 다시 잇는다.**
6. **닫기 코드: 4000~4099 를 쓰고, 4001 은 「다시 오지 마라」, 4000 은 「곧 다시 와라」.** SSE 는 `close` 메시지, 연결 때 401 · 403 은
   4001 과 같다.
7. **채널.** 같은 주소 안에서 값을 나누는 이름이고, 버전 · 기록 · 답 기록을 채널마다 쥔다. 사람마다 다른 값은 채널에 신원을 넣어 준다.
8. **버전이 하나 넘게 건너뛰면 다시 이어 따라잡는다.**
9. **웹소켓은 `hello` 를 10초 안에 받지 못하면 닫는다.**
10. **하위 경로 다섯(§12).**
11. **표준 입출력은 LSP 의 `Content-Length` 머리 꼴로 나눈다.** 언어 서버가 쓰는 꼴이고, JSON-RPC 표준 자체는 나누는 법을 정하지 않는다.
12. **서버 앱이 `ok: false` 로 답한 실패는 앱의 문구를 그대로 쓴다.**
13. **서버에서 그릴 때 `createStream` 은 연결을 열지 않는다.** `typeof window` 로 가르고, `open: "always"` 로 넘긴다.
14. **`welcome` 메시지와 `epoch`.** 따라잡기가 끝난 때와 서버가 다시 뜬 것을 알리려고 더했다.
15. **`snapshot(ctx)` 은 동기 함수다.** 비동기를 받으면 기다리는 동안의 `publish` 가 값에 들었는지 알 수 없다.
16. **앱이 버전을 직접 붙이는 길은 이 판에서 뺐다.** 순번의 빈자리가 건너뛰기 판정과 맞지 않는다.
17. **명령은 그 명령이 낸 바뀜이 `data` 에 든 뒤에 끝난다**(`reply.version`).
18. **SSE 의 `POST` 는 `X-Supa-Connection` 헤더로 스트림 연결을 밝히고, 서버는 `POST` 마다 `authorize` 를 다시 부른다.**
19. **`disposeStores()` 를 더한다.** 시험이 끝날 때 다시 짓지 않고 닫는다.
20. **`createJsonRpc` 는 환경을 가리지 않고 지어질 때 연다.**

## 15. 빌더에게 맡기는 것

- `commands` · `requests` · `handlers` 의 이름과 인자 · 결과 타입을 적는 꼴. §8.1 의 초안처럼 함수 타입으로 적게 할지, 서버 정의의
  타입을 가져다 쓰게 할지(`createStream<typeof terminal>` 같은 꼴, tRPC 처럼). 클라이언트와 서버가 한 저장소에 있으면 뒤쪽이
  자연스럽다.
- 생성기(`tools/codegen.cjs`)가 `createStream` · `createJsonRpc` 정의의 상태 타입을 `StateTypes` 에 싣는지 확인하고, 안 되면 고친다.
- `[DISPOSE]` 를 `build` 에 넣는 자리와, 다시 지을 때 앞 연결의 늦은 메시지가 새 store 를 고치지 않게 하는 막기.
- SSE `fetch` 스트림 읽기의 나누기(줄 · 빈 줄), 서버의 SSE 쓰기.
- 표준 입출력 나누기와 상대의 잘못된 메시지 다루기.
- README 의 새 절.

## 16. 나중에 고려할 것

- **store 를 서버용으로 빌드하는 기능**(사람이 남겼다). store 의 서버 서비스와 따로, store 를 서버용으로 빌드해 「서버에서도 도는
  JSON-RPC 클라이언트」를 그것으로 내는 길. 지금은 §11.4 처럼 `createJsonRpc` 를 React 없이 바로 쓴다.
- 런타임별 웹소켓 어댑터(Bun · Deno · Hono).
- 여러 서버 사이에 기록을 나누는 길(Redis 등).
- 앱이 버전을 직접 붙이는 길(DB 의 순번). 건너뛰기 판정을 `change.prev`(바로 앞 버전)로 바꾸면 순번의 빈자리를 받을 수 있다.
- `isFetching` 과 같은 결로, 연결이 이어졌는지만 보이는 칸이 필요해지면 더한다.
