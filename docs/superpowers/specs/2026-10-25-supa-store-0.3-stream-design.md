# supa-store 0.3 — 서버와 실시간으로 이어진 연결을 store 로 꺼낸다 (설계 진행 중)

- 날짜: 2026-10-25
- 상태: **진행 중.** 대화에서 정한 것과 아직 정하지 않은 것을 모았다. 승인된 설계가 아니다. 남은 물음을 정한 뒤 다시 쓰고
  검토를 거친다.
- 앞선 설계: 같은 폴더 `2026-10-25-supa-store-0.2-design.md` 의 §13 바깥 엔진은 0.3 이 맡는다

## 1. 의도

editor 에는 React 밖에서 스스로 바뀌는 엔진이 셋 있다. 문서 협업 소켓, 터미널 세션, 언어 서버 연결이다. 0.2 까지는 store 의
creator 안에서 엔진을 만들고 `subscribe` 해 `set` 하는 꼴로 감싼다. 그 꼴에는 닫기의 자리가 없어, 개발 모드의 다시 등록과 시험의
`overrideStore` · `resetStores` 로 store 를 다시 지을 때 앞 연결이 열린 채 남는다.

이 판은 그런 연결을 `createResource` 처럼 도우미 하나로 정의하게 한다. 그리고 라이브러리를 만드는 쪽에서 설계하므로, 연결의
약속(프로토콜)까지 supa-store 가 정하고 서버는 그 약속에 맞춰 짓는다. 그 약속을 지키는 서버 도우미도 함께 낸다.

## 2. 대화에서 정한 것

### 2.1 무엇을 쥐는가

- **supa-store 가 쥐는 것은 브라우저 쪽의 연결이다.** 터미널은 서버에서 보면 OS 가 할당한 독립 프로세스지만, 클라이언트에서
  보면 서버와 실시간으로 이어진 연결이다. 브라우저는 OS 프로세스를 띄울 수 없다. 그래서 도우미의 이름은 `createStream` 이다
  (`createProcess` 가 아니다).
- 터미널 · 언어 서버 · 문서 협업 모두 이 하나의 꼴로 감싼다.

### 2.2 생명주기

- **처음 꺼낼 때 연다.** store 가 처음 지어질 때다(0.1.0 의 「처음 꺼낼 때 짓는다」 그대로).
- **다시 지을 때만 닫는다.** 개발 모드의 다시 등록, `overrideStore`, `resetStores` 다. 보는 화면이 없어져도 닫지 않는다.
- **개발 모드와 제품 빌드의 코드를 가르지 않는다.** 제품 빌드에서는 store 를 다시 짓지 않으므로 닫기가 한 번도 일어나지 않는다.
  같은 코드가 제품에서는 「앱 내내 산다」로, 개발에서는 「그 정의 파일을 고칠 때 다시 연다」로 동작한다.
- **개발 중 엔진을 감싼 정의 파일을 고칠 때마다 그 연결이 다시 열리는 것을 받아들인다**(사람이 받아들였다). 터미널이면 열려
  있던 세션이 끝난다. 다른 파일을 고칠 때는 다시 짓지 않는다. 개발 중에 앞 연결을 이어 가는 기능은 지금 두지 않는다.
- supa-store 안에서는 `[USE]` 처럼 상태에 닫기 표식을 두고, 다시 짓기 직전에 앞 상태의 닫기 표식을 찾아 부른다
  (`src/index.ts` 의 `build`).

### 2.3 연결의 약속은 supa-store 가 정한다

쓰는 쪽(앱)이 서버와 약속을 맺는 대신, supa-store 가 약속을 정하고 서버가 그것에 맞춘다. 그래서 다시 잇기 · 다시 이은 뒤의 맞추기
· 메시지 모양이 라이브러리의 규칙이 된다.

| 정하는 것 | 라이브러리가 정하는 방향 | 서버가 맞출 일 |
|---|---|---|
| 다시 이을지 | 「다시 오지 마라」를 뜻하는 닫기 신호를 정한다. 그 밖의 끊김은 모두 다시 잇는다 | 일부러 닫을 때 그 신호로 닫는다 |
| 다시 이은 뒤 | 클라이언트가 마지막으로 받은 판을 보낸다. 서버는 그 뒤의 바뀜이나 지금 값 전체를 보낸다(SSE 의 `Last-Event-ID` 와 같은 생각) | 판 번호를 매기고, 다시 붙은 클라이언트에게 빠진 것을 준다 |
| 간격 | 두 배씩 늘리고 위 끝을 둔다(0.2 의 주기와 같은 규칙) | 없다 |
| 메시지 모양 | 「지금 값 전체」 · 「바뀐 부분」 · 「오류」 · 「명령의 답」 몇 가지 | 그 모양으로 보내고 받는다 |
| 명령 | 클라이언트의 `actions` 가 정해진 꼴로 서버에 간다 | 그 꼴을 받아 처리한다 |

쓰는 쪽 코드는 이만큼으로 줄어든다(초안).

```ts
createStore("infra.terminal", () =>
  createStream<TerminalSession[]>({
    url: "/ws/terminal",
    transport: "ws",                 // 또는 "sse"
    actions: ["open", "write", "kill"],
  }),
);
```

```tsx
const { data, status, error, open } = useStore("infra.terminal", { pick: ["data", "status", "error", "open"] });
```

화면이 받는 칸은 `createResource` 와 같은 이름(`data` · `status` · `error`)이다. 연결 상태는
`"connecting" | "open" | "closed" | "error"` 다.

### 2.4 전송 방식과 서버 도우미

- **웹소켓과 SSE 를 고를 수 있다.** 같은 약속을 쓰므로 쓰는 쪽은 `transport` 하나만 바꾼다.
  - 웹소켓은 양쪽으로 흐른다. HTTP/1.1 요청으로 시작해 Upgrade 로 갈아타는 독립 프로토콜이다(RFC 6455).
  - SSE 는 서버에서 클라이언트로만 흐르는 HTTP 응답이다. 클라이언트의 명령은 따로 HTTP 요청으로 보낸다.
- **서버 도우미를 함께 낸다.** 약속만 문서로 내면 서버마다 판 번호 · 다시 붙기 · 닫기 신호를 손으로 짓게 되어 틀리기 쉽다.
- **바깥 패키지를 쓴다.** Node 에는 웹소켓 서버가 기본으로 없다. 웹소켓 서버 도우미는 `ws` 를 선택 peer 로 둔다(0.1.0 의 `vite`
  · `next` 와 같은 꼴). SSE 서버 도우미는 Node 기본 `http` 로 짓는다. 그래서 「런타임 의존 0개」는 화면 쪽 진입점에만 걸린다.

### 2.5 서버 도우미는 「한 홉」이다 (2026-10-26 사람이 정했다)

- **도메인과 프로세스는 서버 앱이 쥔다.** pty 띄우기, 언어 서버 돌리기, 문서 합치기 같은 일이다. 서버 도우미는 그 안을 모른다.
- **서버 도우미(홉)가 맡는 것은 다섯이다:** 전송 갈아 끼우기, 메시지 모양, 닫기 신호, 살아 있는지 확인(heartbeat), 짧은 기록으로
  이어 주기.
- **버전은 홉이 매긴다.** 앱이 `publish` 할 때마다 그 줄기의 버전을 1씩 올려 붙인다. 앱은 버전을 몰라도 된다.
- **홉은 최근 N 개(또는 최근 몇 초)만 쥔다.** 다시 붙은 클라이언트의 버전이 그 안에 있으면 빠진 것을 준다. 너무 오래됐으면 앱의
  `snapshot()` 으로 지금 값 전체를 받아 준다.
- **앱이 짓는 것은 둘뿐이다:** 바뀌면 `publish`, 그리고 지금 값 전체를 주는 `snapshot`.
- 값이 이미 자기 순번을 가진 경우(DB 의 순번 등) 버전을 앱이 붙이는 꼴은 옵션으로 열어 둘 수 있다.
- 견준 것: Centrifugo(채널마다 최근 기록 · offset 과 epoch 로 이어 받기), Socket.IO 4.6 의 연결 상태 복구(정해진 시간 동안 놓친
  패킷을 쥔다), tRPC v11 구독(웹소켓 · SSE 를 고르고 `tracked(id, data)` 로 앱이 id 를 붙인다), Phoenix Channels, graphql-ws ·
  graphql-sse, SSE 표준의 `Last-Event-ID`. 대체로 약속을 정하고 홉이 데이터를 조금 쥐며 앱은 `publish` 와 `snapshot` 으로
  서버의 개발 부담을 줄이는 꼴이다.

### 2.6 `publish` 는 바뀐 부분을 보낸다 (2026-10-26 사람이 정했다)

- **바뀜의 꼴은 쓰는 쪽이 정한다.** 터미널이면 `{ op: "append", id, chunk }`, 문서면 편집 하나처럼 도메인에 알맞은 꼴이다. 라이브러리가
  JSON Patch 같은 꼴을 정하지 않는다.
- **클라이언트의 `createStream` 이 `reduce(value, change) => value` 를 받아 합친다.** `useReducer` 와 같은 꼴이다. 처음 붙을 때와
  기록 밖으로 밀려났을 때는 `snapshot` 의 값에서 시작하고, 그 뒤의 바뀜을 차례로 `reduce` 한다.
- **`reduce` 를 주지 않으면 바뀜을 「새 값 전체」로 본다.** 작고 통째로 바뀌는 값(연결 상태, 작은 목록)은 이 꼴로 단순하게 쓴다.
- 홉의 짧은 기록은 바뀜을 쥐므로 작다. 다시 붙은 클라이언트에게는 빠진 바뀜을 차례로 준다.

### 2.7 명령은 답을 받는다 (2026-10-26 사람이 정했다)

- **클라이언트가 보낸 명령은 결과나 실패를 돌려받는다.** 약속에 요청 id 와 「답」 메시지가 든다. SSE 에서는 명령이 HTTP 요청으로
  가므로 그 응답이 답이다.
- **화면에서는 자원의 바꾸기와 같은 꼴로 꺼낸다:** `mutate` · `mutateAsync` · `pending` · `error` · `data`(0.2 의 `MutationView`).
- 까닭: 터미널은 세션 id, 언어 서버는 완성 목록 · 정의 위치, 문서 협업은 편집이 받아들여졌는지가 필요하다. 언어 서버는 거의 모든
  일이 묻고 답 받기다.
- **끊긴 동안 부른 명령은 곧바로 실패한다**(2026-10-26 사람이 정했다). `mutateAsync` 가 「연결이 끊겼다」로 거절하고 `error` 칸에도
  남는다. 쥐었다 다시 보내지 않는다. 같은 명령이 두 번 실행될 위험을 없애고, 중복 거르기를 앱의 일로 만들지 않으려는 것이다.
- **답의 제한 시간은 기본 30초다.** `createStream({ timeout })` 으로 연결마다, `actions: { 이름: { timeout } }` 으로 명령마다 바꾼다.
  지나면 그 명령은 실패하고 뒤늦게 온 답은 버린다.
- **홉이 최근 명령의 요청 id 와 답을 쥔다**(2026-10-26 사람이 정했다 — 홉이 가져가기에 무겁지 않다). 쥐는 기간은 바뀜의 짧은 기록과
  같은 규칙이다. 보낸 뒤 답을 받기 전에 끊긴 명령은 `pending` 으로 남고, 다시 이어지면 클라이언트가 홉에 그 요청 id 를 묻는다.
  - 홉이 답을 쥐고 있으면 그 답으로 끝낸다(성공 또는 실패).
  - 받은 적이 없으면 「연결 끊김. 명령 실패」로 끝낸다. 다시 보내도 안전하다.
  - 처리하는 중이면 답을 기다린다.
  - 홉이 다시 떠서 기록을 잃었으면 「연결 끊김. 알 수 없음」으로 끝낸다.
  손으로 다시 보낼 때 같은 요청 id 로 보내면 홉이 앞 답을 돌려준다. 그래서 중복 거르기는 앱의 일이 되지 않고, §2.5 의 「앱은
  `publish` 와 `snapshot` 만 짓는다」가 그대로다. 견준 것: HTTP `Idempotency-Key`(Stripe), MQTT QoS 2.

### 2.8 문구 (2026-10-26 사람이 정했다)

| 자리 | 언제 보이나 | 문구 |
|---|---|---|
| 연결의 `error` | 연결이 끊겨 다시 잇는 동안 | 연결 끊김. 재시도 중.. |
| 명령의 `error` · `mutateAsync` 의 거절 | 끊긴 동안 부른 명령, 또는 다시 이은 뒤 홉이 받은 적 없다고 답한 명령 | 연결 끊김. 명령 실패 |
| 같은 자리 | 보낸 뒤 답을 받기 전에 끊겼고 다시 이은 뒤에도 결과를 확인하지 못한 명령 | 연결 끊김. 알 수 없음 |
| 같은 자리 | 제한 시간(기본 30초) 안에 답이 오지 않은 명령 | 응답 지연 |

「재시도 중」은 연결에만 쓴다. 명령은 다시 보내지 않으므로, 명령의 문구에 쓰면 사용자가 처리되리라 믿고 기다리게 된다.

### 2.9 서버 도우미가 붙는 자리 (2026-10-26 사람이 정했다)

- **두 진입점을 함께 낸다.**
  - Node `http` 서버에 붙는 꼴: `attachStream(httpServer, { path, stream })`. Express · Fastify · Koa 처럼 밑에 Node `http` 서버를 둔
    틀은 이것으로 붙는다.
  - Web 표준 처리기 꼴: `(req: Request) => Response`. Hono · Next 라우트 처리기 · Bun · Deno 에 건다.
- **약속 처리(버전 · 바뀜의 기록 · 명령의 답 기록 · heartbeat)는 전송과 떼어 한 벌만 짓는다.** 두 진입점은 그 위의 겉이다.
- **Web 표준 꼴은 SSE 만 받는다**(명령은 HTTP 요청으로). 웹소켓은 Node `http` 꼴에서만 받는다. Web 표준에는 웹소켓으로 갈아타는
  길이 없어 런타임마다(Bun `server.upgrade` · Deno `Deno.upgradeWebSocket` · Hono 의 런타임별 도우미 · Cloudflare
  `WebSocketPair`) 다르고, Next 라우트 처리기는 받지 못한다. 같은 약속이라 Web 표준 틀의 앱은 `transport: "sse"` 로 같은 기능을
  쓴다. 런타임별 웹소켓 어댑터는 요청이 생기면 더한다.

### 2.10 인증 (2026-10-26 사람이 정했다)

- **홉은 판단하지 않는다.** 판단은 앱이 하고, 홉은 판단을 부를 자리와 신원을 실어 나를 길만 준다.
- **클라이언트:** `createStream({ auth: () => token })`. 웹소켓은 그 값을 연결 뒤 첫 메시지로, SSE 는 `Authorization` 헤더로 싣는다.
  브라우저의 `WebSocket` · `EventSource` 는 헤더를 붙일 수 없으므로, SSE 는 `EventSource` 대신 `fetch` 의 스트림으로 받는다.
  `auth` 를 주지 않으면 쿠키만 쓴다.
- **다시 이을 때마다 `auth()` 를 다시 부른다.** 그사이 바뀐 토큰으로 이어진다.
- **서버:** `authorize(ctx) => 신원 | 거절`. 거절이면 §2.3 의 「다시 오지 마라」 닫기 신호로 닫아 클라이언트가 다시 잇지 않는다.
  신원은 `snapshot(ctx)` 과 명령 처리기로 넘어가, 앱이 사람마다 다른 값을 줄 수 있다.
- **토큰을 주소의 쿼리로 싣지 않는다.** 서버 접근 기록과 프록시 기록에 남기 때문이다.

## 3. 아직 정하지 않은 것

1. ~~서버 도우미가 붙는 서버 틀~~ — §2.9 로 정했다(Web 표준 꼴에서 웹소켓을 어디까지 받는지는 남았다). 원래 물음: Node `http` 만인가, Express · Hono · Next 라우트 처리기까지인가. 진입점 이름(`supa-store/server`
   등)도 함께 정한다.
2. ~~서버 쪽 상태를 누가 쥐는가~~ — §2.5 로 정했다.
3. ~~「바뀐 부분」의 모양~~ — §2.6 으로 정했다. 원래 물음: 값 전체를 늘 보내는가, 바뀐 부분만 보낼 꼴(예: JSON Patch)을 정하는가.
4. ~~명령의 답~~ — §2.7 로 정했다(끊긴 동안 · 제한 시간은 남았다). 원래 물음: `actions` 를 부르면 결과를 돌려받는가(0.2 의 `mutateAsync` 처럼), 보내기만 하는가. 답을 받으면 요청 id 와
   제한 시간이 필요하다.
5. ~~인증~~ — §2.10 으로 정했다. 원래 물음: 연결을 열 때 무엇으로 누구인지 알리는가. 다시 이을 때 그것을 어떻게 다시 쓰는가.
6. **닫기 신호의 구체 값.** 웹소켓 닫기 코드(4000 번대)와 SSE 에서의 같은 뜻.
7. **언어 서버처럼 이미 표준 프로토콜(LSP)이 있는 연결.** 그 위에 이 약속을 한 겹 씌우는가, 따로 다루는가.
8. **다시 잇는 동안 store 의 값.** 마지막 값을 쥐고 있는가, 비우는가. `status` 는 무엇으로 보이는가.
9. **시험.** 서버 도우미와 클라이언트를 함께 띄우는 시험을 어떻게 짓는가. 선택 peer `ws` 를 시험에서 어떻게 들이는가.

## 4. 다른 라이브러리의 생명주기 — 고를 때 견준 것

| 라이브러리 | 바깥 자원을 여는 때 | 바깥 자원을 닫는 때 |
|---|---|---|
| Zustand | 모듈을 읽거나 store 를 만들 때 | 라이브러리가 닫지 않는다 |
| Pinia | store 를 처음 쓸 때 | `$dispose()` 를 부를 때 |
| Jotai(`onMount`) | 첫 구독이 생길 때 | 마지막 구독이 풀릴 때 |
| Nanostores(`onMount`) | 첫 구독이 생길 때 | 마지막 구독이 풀리고 약 1초 뒤 |
| RTK Query(`onCacheEntryAdded`) | 캐시 칸이 처음 생길 때 | 쓰는 쪽이 없고 일정 시간(기본 60초) 뒤 |

supa-store 는 Zustand · Pinia 처럼 앱 내내 살리는 쪽을 골랐다. 다만 다시 지을 때는 닫는다. Vite 의
`import.meta.hot.dispose` 가 하는 일을 store 단위로 하는 셈이다.
