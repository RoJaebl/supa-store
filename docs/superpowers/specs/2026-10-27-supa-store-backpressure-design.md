# supa-store — 읽지 않는 연결의 버퍼 쌓임을 막는다 (짧은 설계)

- 날짜: 2026-10-27
- 상태: **검토 전**
- 앞선 설계: 같은 폴더 `2026-10-25-supa-store-0.3-stream-design.md` §16 나중에 고려할 것(「읽지 않는 클라이언트 쪽 버퍼 쌓임」, 0.3.x 로 미뤘다)

## 의도와 까닭

0.3 의 홉(`createStreamServer`)은 `publish` 마다 그 채널의 모든 연결에 보낸다. 받는 쪽이 읽고 있는지는 보지 않는다. 그래서 읽지 않는
클라이언트나 반쯤 끊긴 연결에는 TCP 가 오류를 낼 때까지 버퍼가 쌓인다(Node `res.write` · Web `enqueue` · ws 버퍼 모두). 이것을 막는다.

연결을 4000(다시 와라)으로 닫으면 클라이언트는 마지막 버전으로 다시 잇고, 짧은 기록이나 snapshot 으로 따라잡는다(0.3 §7.2 버전과 짧은
기록). 그래서 끊어도 값을 잃지 않는다.

## 목표 · 하지 않는 것

- 목표: 연결 하나에 쌓인 바이트가 한도를 넘으면 그 연결을 4000 으로 닫는다. 웹소켓은 `pong` 이 끊기면 닫는다.
- 하지 않는 것: 느리게 읽는 것이 정상인 클라이언트를 따로 다루기(2026-10-27 사람이 「아직은 아니다」로 정했다). 메시지를 건너뛰기.

## 고려한 길

| 길 | 이 길이 막는 것 | 고른 까닭 또는 버린 까닭 |
|---|---|---|
| A. 쌓인 양에 위 끝을 둔다 | 세 전송 모두의 메모리 쌓임 | **골랐다.** 미룬 까닭이 메모리였다 |
| B. 웹소켓 `pong` 이 끊기면 닫는다 | `publish` 가 없는 채널의 반쯤 끊긴 웹소켓 연결 | **함께 골랐다**(사람이 정했다). 연결 수까지 막는다 |
| 보내지 않고 건너뛴다 | — | 버렸다. 클라이언트가 버전의 빈자리를 보고 어차피 다시 잇는데, 그 사이 값이 어긋난 채로 남는다 |

## 정한 것

**A. `maxBuffered`**

```ts
createStreamServer({ ..., maxBuffered: 4 * 1024 * 1024 })   // 생략하면 4 MiB. Infinity 면 재지 않는다
```

- `Conn` 에 `buffered(): number` 칸을 더한다. 아직 나가지 못한 바이트 수다.
  - ws: `ws.bufferedAmount`
  - Node SSE: `res.writableLength`
  - Web SSE: 응답 몸통을 `ByteLengthQueuingStrategy` 로 짓고, 쌓인 바이트를 센다(`enqueue` 한 바이트 − 읽힌 바이트, 또는 `highWaterMark − desiredSize`)
- **보내기 직전에 잰다.** 이미 쌓인 양이 `maxBuffered` 를 넘었으면 그 메시지를 보내지 않고 연결을 4000 으로 닫는다. 보낸 뒤에 재면
  한도보다 큰 snapshot 하나가 보낼 때마다 연결을 닫아, 다시 잇고 또 닫히는 일이 끝없이 되풀이된다. 보내기 전에 재면 받는 쪽이 앞의
  것을 읽고 있는 한 큰 메시지 하나는 지나간다.
- 홉은 `conn.send` 를 부르는 자리 한 곳에서만 본다(`publish` · history · snapshot · ping · reply · request 모두 그 길을 지난다).
- 닫는 까닭 문구: `"버퍼가 넘쳤다"`.

**B. 웹소켓의 살아 있음**

- 홉은 웹소켓 연결마다 마지막으로 무엇이든 받은 때(`pong`, 명령, 답)를 적는다. attach 때부터 센다.
- 25초 `ping` 을 보낼 때 마지막으로 받은 뒤 60초(`DEFAULTS.idleMs`)가 지났으면 `ping` 대신 4000 으로 닫는다. 문구: `"응답이 없다"`.
- SSE 는 받는 줄이 없어 `pong` 이 없으므로 B 를 걸지 않는다(A 만 건다).

## Claude 가 정한 것 — 사람이 확인할 것

1. 기본 한도는 4 MiB 다. 받는 메시지 한도(1 MiB)의 네 배로, 보통 크기의 snapshot 과 바뀜 몇 개가 쌓일 자리다.
2. 이 고침은 따로 버전을 올리지 않고 아직 내지 않은 0.4.0 에 함께 담는다.
3. B 의 판정은 `ping` 을 보내는 때에만 한다. 그래서 끊긴 뒤 닫히기까지 60~85초가 걸린다. 0.3 클라이언트의 60초와 어긋나지 않는다.
4. 홉 쪽 시험은 가짜 `Conn` 의 `buffered()` 로, 전송 쪽 시험은 실제 ws · Node http 로 읽지 않는 클라이언트를 붙여 한다.
5. `Conn.buffered` 는 선택 칸이다(빌더 · 마지막 검토가 짚었다). 꼭 있어야 하는 칸으로 두면 공개 타입이 깨지고, JS 로 짓거나
   `as Conn` 으로 넘긴 Conn 이 첫 send 에서 던진다. 비워 두면 그 연결은 한도를 재지 않는다.

## 빌더에게 맡기는 것

- Web SSE 에서 쌓인 바이트를 세는 정확한 방법(위 둘 가운데 맞는 것).
- 시험에서 시간을 줄이는 방법(0.3 의 `TIMING` 꼴 또는 가짜 타이머).

## 나중에 고려할 것

- SSE 를 4000 으로 닫아도 반쯤 끊긴 클라이언트는 TCP 가 죽을 때까지 쌓인 한도만큼의 버퍼가 남는다. 닫은 뒤 몇 초 안에 응답이 끝나지
  않으면 소켓을 destroy 하는 길로 막는다.
- 따라잡기 기록을 한 번에 보내므로, 기록이 한도보다 크면 따라잡기 도중에 닫혔다가 다시 이어 받는다.
- 0.3 클라이언트와 홉을 실제로 이어, 「버퍼가 넘쳤다」로 닫힌 뒤 다시 이어 따라잡는 것을 끝에서 끝까지 보는 시험이 없다. 클라이언트는 4000 을 문구와 상관없이 같은 길로 다루고 그 길은 기존 시험이 덮는다.
